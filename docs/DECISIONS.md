## D-001 Hosting and deploy target: Cloudflare Workers with static assets (Workers-only adapter)

- **Context.** Spec 12.1 recommends Astro with Cloudflare static assets plus Workers; Phase 0 says "Cloudflare projects". `@astrojs/cloudflare` 14.4.1 targets Workers only (Pages support was removed in v13). Cloudflare's own Pages page says to start new projects on Workers. Vercel Hobby is non-commercial. No Free-plan commercial ban was found in Cloudflare's terms, but section 2.2.1(h) bars processing or collecting card data on a web property receiving Free Services.
- **Decision.** Build one Worker with static assets: Astro 7.x, `@astrojs/cloudflare` 14.x, `wrangler deploy`. Create a Worker project, not a Pages project. Prerender every public content page. Use `prerender = false` only for `/go/*`, form endpoints, the beacon, `/api/*`, live status, Razorpay webhooks (P2) and privileged admin actions. Set the adapter's `imageService` to `passthrough` or `compile` (images are external YouTube thumbnails) and do not use Astro sessions (no KV). Launch on the Free plan. The site never renders its own card or UPI-credential fields.
  - **Prerender in Node by default (G0, verified 2026-10-21).** The project sets `prerenderEnvironment: 'node'` (override with `PS_PRERENDER_ENV=workerd`); the adapter's own default is `workerd`. Measured on the dev PC at 15,000 pages: 97.3 s and 754 MB peak with `node` versus 859.8 s and 1,455 MB with `workerd`, with identical output; at 8,000 pages 89.0 s and 671 MB versus 482.6 s and 1,236 MB. Consequence: prerendered pages must not import `cloudflare:workers`; runtime routes (`prerender = false`) still run in workerd. Full numbers: the "G0 outcome" under D-003 and `docs/G0_RESULT.md`.
- **Consequences.** Free limits apply (D-009). A `*.workers.dev` URL exists as a fallback and is marked noindex (D-023). Before Phase 2 go-live, get Cloudflare's written confirmation that Razorpay-hosted Checkout on a Free-plan zone is acceptable, or budget the paid plan (D-036). G0 found that `session: false` in `astro.config.mjs` stops the adapter from provisioning the SESSION KV (the generated config has `kv_namespaces: []`), so no KV-edit scope is expected on the deploy token; the real deploy test from CI is still pending (OT-02).
- **Status.** adopted.
- **Sources.** VF-A2, VF-A3, VF-A10, VF-A11, VF-A21, VF-A23, VF-A27.
- **Superseded by D-097 (2026-10-22).** hosting moves to Vercel (owner decision). The Cloudflare Workers adapter, `wrangler deploy`, `*.workers.dev` fallback and the 20,000-file Free cap no longer apply. Kept as history.

## D-002 Toolchain pins and supply-chain policy

- **Context.** TypeScript 7 breaks `astro check`; Tailwind 4 replaces the old integration; LHCI bundles an old Lighthouse; recent npm worm campaigns spread through install scripts; secrets are present in CI.
- **Decision.**
  - Node 24 with `.nvmrc`; Astro 7.4.x; `@astrojs/cloudflare` 14.4.x; `@astrojs/react` 7.1.x with React 19; Tailwind 4.3.x through `@tailwindcss/vite`, tokens in a CSS `@theme` block (replaces "map into the Tailwind theme"). These are the latest versions found on 2026-10-20 and are targets, not the installed pins.
  - **Versions rule (M0, verified 2026-10-21).** `.npmrc` `min-release-age=7` beats the "latest" list: npm refuses a version published less than 7 days earlier. Several targets above were that new on 2026-10-20, so the first install took lower versions than the targets (for example astro 7.3.8, `@astrojs/cloudflare` 14.3.4, `@astrojs/react` 7.0.1, react 19.3.0, wrangler 4.150.0, vitest 5.0.4). The installed exact versions are in `VERIFIED_FACTS.md` section 1b. Re-check at the start of each milestone (spec rule 4); after any pin moves, re-run the quick G0 checks (dev, build, `wrangler deploy --dry-run`, `check`, `test`). Only the lead changes dependencies. Packages not used yet (Playwright, Lighthouse tooling, `supabase-js`, `zod`, `jose`, TanStack and others) were not installed at M0 close: pin each exact version when it is first needed.
  - **`@types/node` is required.** `@types/node` 24.19.2 was added as an exact-pinned devDependency (type definitions only) because `astro check` on TypeScript 6.0.3 fails on `process` and `node:` imports without it.
  - **TypeScript pinned to ~6.0.3** and `@astrojs/check` 0.9.11; Dependabot or Renovate ignores TypeScript major 7 until Astro announces support.
  - Vitest with its own config that does not load the Cloudflare plugin; Playwright (browsers are about 500 MB: Claude asks before downloading); Lighthouse: try `@lhci/cli` 0.15.1 on Node 24, otherwise run `lighthouse` 13 directly; record the version that produced the 90/95 scores.
  - `.npmrc` with `ignore-scripts=true` (allow-list only packages that need a build step) and `min-release-age=7` (verify with `npm config get min-release-age`; npm 11.19.0 is installed); `npm ci` with a committed lockfile and exact pins; review lockfile diffs; minimal dependencies (React only where an island needs it). **Allow-list at G0: none needed.** `esbuild`, `workerd` and `sharp` arrive as platform packages and run with install scripts off, so no `npm rebuild` was needed; re-confirm on the Linux CI runner at the first CI run.
  - GitHub Actions: pin third-party actions to commit SHAs, `permissions: contents: read` by default, never `pull_request_target` with secrets, no secrets in PR or preview builds.
  - **Secret scanning (corrected 2026-10-21).** GitHub's own secret scanning alerts and push protection are NOT available on a private repository on the Free plan: they belong to GitHub Secret Protection (paid), free for public repositories only (VF-A30). This record used to say they would be on; that is withdrawn. The replacement is **gitleaks in CI** (the `secret-scan` job, `gitleaks/gitleaks-action` pinned to a commit SHA, config `.gitleaks.toml`; no licence key is needed because the repository belongs to a personal account, VF-A31) **plus a local pre-commit hook**. Downloading the gitleaks binary for the hook needs the owner's approval (CLAUDE.md ask-first list); the CI action does not. Until the hook exists, CI is the net. **Never make the repository public to get GitHub's scanning:** the test fixtures contain real players' names (D-017, D-038). Turning on paid Secret Protection would be a spend (D-036).
  - Self-host fonts through Fontsource (Barlow Condensed static 700 and 800, Inter variable, Noto Sans Tamil static 400 and 600); put Noto Sans Tamil in the heading font stack because Barlow has no Tamil glyphs; keep the OFL licence files in `docs/licenses`; Lucide through `@lucide/astro`; `qrcode` with SVG output; a licence checker in CI; a font budget (about 150 KB on a typical English page).
  - Pin `zod`, `jose`, TanStack and react-hook-form at M0 (no versions are given in the inputs).
- **Consequences.** A bare `npm install typescript` is forbidden. `ignore-scripts` needs no allow-list so far (G0); the Linux CI run re-confirms. Versions are re-checked at build time (spec rule 4), and the installed versions can lag the targets by the `min-release-age` window.
- **Amended by D-073 (2026-10-21).** The gitleaks configuration has four more rules (database URL with a password, bare Telegram token, Turnstile secret shape, Resend key) and `.gitignore` gained secret-file and scratch-file patterns.
- **Status.** adopted.
- **Sources.** VF-A4, VF-A5, VF-A27, VF-A30, VF-A31, VF-F13, VF-F14, pinned versions table (section 1) and installed versions (section 1b), SA-M27, SA-N14 to SA-N19; D-040.
- **Amended by D-097 (2026-10-22).** `@astrojs/cloudflare` and `wrangler` pins are replaced by `@astrojs/vercel` (the pin is set by the lead under the 7-day rule); the `.npmrc` policy is unchanged.

## D-003 Windows 10 tooling gate (G0) and fallback

- **Context.** Wrangler and workerd officially support macOS 13.5+, Windows 11 and Linux glibc 2.35, not Windows 10. The dev machine is Windows 10 Pro build 19042 with an Intel i3-4030U (2 cores, 4 threads) and 8.1 GB RAM (planned as "7.9 GB and 4 CPUs", corrected from the G0 measurements); the project path contains a space; no Docker. `astro dev`, `astro preview` and prerendering run in workerd by default.
- **Decision.** M0 starts with a 2-4 hour smoke test, a **go/no-go gate (G0)**, before any feature work:
  1. Scaffold Astro 7 with the adapter (test inside the current spaced path first).
  2. `astro dev` and `astro build` with 8,000-15,000 generated pages; record peak RAM and time with `prerenderEnvironment` set to `node` and to `workerd`; set `NODE_OPTIONS=--max-old-space-size=4096` if needed.
  3. `wrangler deploy --dry-run`, then a real hello-world deploy to workers.dev **from GitHub Actions**.
  4. Vitest, `astro check` (TypeScript 6.0.3), Playwright smoke, Lighthouse on Node 24.
  - Pass: dev server starts and stays up, build completes, dry-run works. If it fails, take the fallback ladder in order: (a) `prerenderEnvironment: node` plus preview URLs instead of local workerd; (b) all builds, deploys and heavy suites on Linux in GitHub Actions, the PC only edits code and runs unit tests, Claude verifies through preview URLs; (c) only with the owner's approval, WSL2 (the Windows 10 floor for WSL2 is unverified and the machine has about 8 GB RAM) or a Windows 11 upgrade; (d) otherwise stop and report.
  - Repo hygiene: `.gitattributes` with `* text=auto eol=lf`; `git config core.longpaths true`; Node or `tsx` scripts and `cross-env` only (no POSIX-only shell in npm scripts); move the repo to a path without a space (for example `C:\dev\power-smash`) only if a tool fails because of the space; a Windows Defender exclusion only with the owner's approval.
- **Consequences.** About half a day of M0 is the gate; fallback (b) makes local iteration slower but removes the OS risk. Any outcome is recorded here.
- **Status.** adopted. Outcome: PASS on 2026-10-20 (local checks); see "G0 outcome" below, `docs/G0_RESULT.md` and D-040.
- **Sources.** VF-A6 to VF-A9, VF-A24, VF-A27, VF-A28; SA-C13.

### G0 outcome (2026-10-20)

- **Verdict: PASS (local checks).** Wrangler and workerd run on this Windows 10 build 19042 PC (i3-4030U, 8.1 GB, Node 24.20.0), in the spaced path, with Astro 7.3.8 and `@astrojs/cloudflare` 14.3.4. The fallback ladder was not needed. Full evidence: `docs/G0_RESULT.md`. Still PENDING because they need the owner: the real hello-world deploy from GitHub Actions (OT-02), the Playwright smoke test and Lighthouse (500 MB browser download needs approval), and build timing on a GitHub runner (VF-A24).
- **Measured.** `astro dev` ready in 26-30 s and stayed up 62.5 s with every fetch of the hello page, a generated page and `/api/health` returning 200, for both prerender modes (peak 974-1,200 MB); `astro preview` ready in 12 s. `astro build` (exit 0 each time, `NODE_OPTIONS` never needed): 8,000 pages 482.6 s / 1,236 MB peak with `workerd` and 89.0 s / 671 MB with `node`; 15,000 pages 859.8 s / 1,455 MB with `workerd` and 97.3 s / 754 MB with `node`. Output HTML is identical in both modes. `wrangler deploy --dry-run` (no login) exit 0: 655 KiB bundle, 660 KiB / gzip 172 KiB total upload, no KV; 73 s at 8,000 pages and 153 s at 15,000 pages. `astro check` on TypeScript 6.0.3: 0 errors (48.9 s). Vitest with its own config (no Cloudflare plugin): green.
- **File count (D-009).** One page is one file, so `dist/client` holds pages plus about 10 files: 8,008 uploaded assets at 8,000 pages (40% of the 20,000 Free limit) and 15,008 at 15,000 pages (75%; about 15,025 files in all of `dist/` with the server folder). 15,000 pages therefore exceed the D-009 fail line of 14,000, and the budget is in effect a page budget (about 14,000 pages minus search index, fonts, sitemaps and other assets). The D-009 gate must count regular files in `dist/client` only: wrangler's "Read N files" line also counts folders (30,012 for 15,000 pages) and overstates by about 2x. Expected real page counts are unknown until M2 profiling (about 1,900 videos). If the plan total nears 14,000, trim pages (D-013 tiers) or take Workers Paid (100,000 files, D-036).
- **Install-script allow-list needed: none.** `esbuild`, `workerd` and `sharp` arrive as platform optional dependencies (`@esbuild/win32-x64`, `@cloudflare/workerd-windows-64`, `@img/sharp-win32-x64`) and run with `ignore-scripts=true`; no `npm rebuild` was needed. Re-confirm on the Linux CI runner at the first CI run. One dependency was added: `@types/node` 24.19.2 (devDependency, exact, type definitions only), because `astro check` on TypeScript 6.0.3 fails on `process` and `node:` imports without it.
- **Final adapter config.** `cloudflare({ imageService: 'passthrough', prerenderEnvironment })` with `prerenderEnvironment` defaulting to **`node`** (override: `PS_PRERENDER_ENV=workerd`; reason: 5.4x to 8.8x faster and about half the memory, same output; consequence: prerendered pages must not import `cloudflare:workers`; runtime routes still run in workerd). `session: false` in `astro.config.mjs`, which the Astro 7.3.8 config accepts: without it the adapter adds an auto-provisioned `SESSION` KV binding; with it the generated config has `kv_namespaces: []`, so the D-001 risk of a KV-edit scope on the deploy token goes away. `wrangler.jsonc`: `name` `power-smash`, `main` `@astrojs/cloudflare/entrypoints/server` (Astro docs value; Cloudflare's own Astro guide still shows the older `./dist/_worker.js/index.js` setup), `compatibility_date` `2026-10-01` (the installed workerd is dated 2026-10-06, so the real date would be in its future), `compatibility_flags` `["nodejs_compat"]`. `output` stays the default (static) with `prerender = false` on runtime routes. No `.assetsignore` is hand-written: the adapter generates it.
- **Cron Triggers on Workers Free (official limits page, https://developers.cloudflare.com/workers/platform/limits/).** Available: 5 Cron Triggers per account (Paid 250) and 10 ms CPU per invocation (Paid 30 s under a 1-hour interval, 15 min otherwise). The adapter's default entry exports only `fetch`, so the cron milestone needs a custom entry file (`scheduled` plus `fetch` re-exported from `@astrojs/cloudflare/handler`) or a second small Worker; not tested in G0. Whether cron runs count toward the 100,000 requests a day is unverified.
- **Recommended change to the ladder.** Fallback (a) (`prerenderEnvironment: node`) is adopted as the default now, because it is faster, not because anything failed; the ladder's remaining steps (b) to (d) stay as written for the case where a later Wrangler, workerd or Vite release breaks on Windows 10 (Wrangler officially supports Windows 11 only, so keep production builds and deploys in CI, D-008). Re-run the dev and dry-run checks whenever Astro, the adapter, Wrangler or workerd pins move. Add to the Pass line: the D-009 file count is taken from `dist/client` regular files.
- **Amended by D-097 (2026-10-22).** the wrangler and workerd Windows 10 question is moot for the host (builds run on Vercel or GitHub Linux runners). G0 stays as the record of the local toolchain; whether `vercel build` runs locally on Windows 10 is unverified (VF-V7).

## D-004 Dev, preview and test database approach (no Docker)

- **Context.** Spec 12.3 assumes "Local (Supabase CLI)". `supabase start` needs Docker; none is installed and the machine is too small for the full stack plus tooling. Free Supabase allows two active projects. Region cannot be changed after creation.
- **Decision.**
  - Exactly two Free projects, both in **South Asia (Mumbai, ap-south-1)**: `powersmash-prod` and `powersmash-dev`. At creation leave "Automatically expose new tables" **unchecked**. Run the documented opt-in default-privileges SQL in dev on day 1 so dev behaves like production.
  - Dev holds fictional seed data only (never the real WhatsApp number, the personal Gmail or real titles). Previews (Workers version preview URLs, posted in chat) use dev, send `X-Robots-Tag: noindex`, use Cloudflare's Turnstile test keys and a wildcard Auth redirect pattern.
  - The CLI is a dev dependency (`npx supabase`): `link`, `db push`, `migration list`, `gen types --linked`. Do not plan on `db pull`, `db diff`, `db dump`, `db reset` or `start` locally.
  - RLS and grant tests, migration replay from empty, and the restore drill run in GitHub Actions on Ubuntu (Docker is available there). CI refuses to run migrations against production except from `main`.
  - The sync writes a `sync_runs` row on every run (a real database write) so production never pauses; dev will pause when idle (document "Resume project").
  - Docker is never installed on the owner's PC.
  - **Worker placement hint.** Workers that call the Supabase Mumbai database get a Cloudflare placement hint (`placement.region` in the form `aws:<region>`, or `placement.host` / `placement.hostname` probes) or Smart Placement. Checked against Cloudflare's official Smart Placement docs on 2026-10-20: available on all Workers plans; does not apply to static assets, which are always served nearest the visitor. The docs' region examples do not include `ap-south-1` (they point to the AWS, GCP and Azure region lists), so M0 tests that the hint is accepted and measures the latency before keeping it (SPEC_AUDIT section 6 item 3).
- **Consequences.** The two-project cap leaves no scratch project (see D-011). The owner must have no other Free Supabase projects. Dev is shared by all previews.
- **Amended by D-047 and D-074 (2026-10-21).** Previews and local runs may use Cloudflare's Turnstile test secrets only with `TURNSTILE_ALLOW_TEST_KEYS=true`; the local `.env` holds fake and published-test values only.
- **Status.** adopted.

## D-005 Supabase keys, GRANTs, `api` views and function rules

- **Context.** RLS cannot hide columns. Views bypass RLS by default (lint 0010). The Data API stopped auto-exposing tables (new projects since 2026-05-30; all existing projects 2026-10-30). Function `EXECUTE` is granted to PUBLIC by default and this change does not close it. New projects only have publishable and secret keys. The Data API returns at most 1,000 rows per request.
- **Decision.**
  1. Env names: `PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_PUBLISHABLE_KEY` (value `sb_publishable_...`), `SUPABASE_SECRET_KEY` (value `sb_secret_...`); legacy `anon` and `service_role` names are not used (D-027).
  2. Every migration that creates a table, view, function or sequence enables RLS, adds policies and includes explicit GRANTs. `REVOKE ALL` on all base tables from `anon` and `authenticated`; `service_role` gets only what Workers and the sync need; prefer uuid or identity keys (sequence USAGE).
  3. Public data is exposed only through views in a dedicated `api` schema with explicit column lists (no `select *`), filtering `visibility = 'public'`, parse status and age status, and applying protected-player masking inside the SQL. Views are owned by a restricted role without BYPASSRLS; `anon` gets SELECT on these views only. The Supabase lint 0010 warning on these deliberate views is a documented exception; where a view can be `security_invoker = on` with column-level grants without breaking the masking, prefer that. Private contact data lives in separate tables (`tournament_private`, `sponsor_contacts` and similar) that `anon` cannot reach.
  4. Functions live in an unexposed schema (`app`) where possible. Any function in an exposed schema gets `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` and then explicit grants; SECURITY DEFINER only with a fixed `search_path`.
  5. The static build reads the `api` views with the **publishable key**; the build job never holds the secret key.
  6. CI tests: (a) as `anon` through PostgREST, `select *` on every base table fails; (b) each `api` view's columns equal a committed allowlist and no column is named like phone, email or contact; (c) every RPC outside an allowlist is denied to `anon`; (d) `POST /auth/v1/signup` is rejected; (e) from M2, editor-role attempts on `profiles.role`, subscribers, leads and audit rows are denied.
  7. Every list read uses a paginated helper (`.range()` pages of 1,000, stable order) and CI asserts the fetched count equals `count(*)`; a fixture with more than 1,000 rows proves it.
  8. Install `pg_trgm` and `unaccent` in the `extensions` schema and schema-qualify calls; test `similarity()` on three Tamil strings on the real instance (D-017).
- **Consequences.** More migration boilerplate; M0 builds the test harness first so every later table is checked automatically.
- **Amended by D-049 (2026-10-21).** The M1 private tables (leads, events and others) live in schema `public` with RLS, no policies and `service_role`-only grants; `api` stays for public views.
- **Status.** adopted.
- **Sources.** VF-B7 to VF-B9, VF-B11, VF-B16; SA-C04, SA-M51.

## D-006 Auth, MFA and admin architecture

- **Context.** The SPA could call PostgREST directly; sign-ups may be open; the default Auth SMTP cannot invite users; role claims could come from user-editable metadata; MFA is not enforced by Supabase; the Worker's JWT method is unspecified.
- **Decision.**
  - Sign-ups disabled; users are created from the dashboard or Admin API (the owner's M0 login is the owner user created in the Supabase dashboard), or invited after Resend SMTP is configured at M1 go-live (D-022; needs a verified domain). First owner bootstrap plus a TOTP enrolment page in the admin; the owner enrols **two TOTP factors** (phone plus a second device); a RUNBOOK "MFA reset" procedure uses the service role.
  - Role comes only from `profiles.role` through a SECURITY DEFINER function in an unexposed schema (never `user_metadata`). Owner-only tables, RPCs and every Worker endpoint require `aal2`.
  - Workers verify bearer JWTs with `jose` against the project's JWKS (or `getClaims`), check `exp`, `iss` and `aud`, then look up the role; the secret and publishable keys are never used as bearer tokens. CORS allows only the admin origin; bearer-header auth, no cookies.
  - Admin is its own Vite and React SPA with hash routing, emitted under `/admin/`, served from its own hostname `admin.<domain>` (the `/admin/` path on workers.dev until the domain is live). `_headers` and middleware: noindex, no-store, `frame-ancestors 'none'`, strict CSP; no `dangerouslySetInnerHTML` anywhere.
  - Single-table edits go straight under RLS. Multi-table or privileged actions are SECURITY DEFINER RPCs (`merge_players`, `split_player`, `rename_player`, `approve_tournament`, `mark_paid`, `emergency_hide`) that run in one transaction, check role and `aal`, and write the audit entry.
  - Audit through generic AFTER triggers using `auth.uid()`; append-only (REVOKE UPDATE, DELETE, TRUNCATE from app roles); diffs redact phone and email; Telegram alert on role changes, CSV exports and UPI or WhatsApp setting changes.
- **Consequences.** Slightly more database code; admin cannot be bypassed from the browser; a lost phone is recoverable.
- **Amended by D-086 and D-087 (2026-10-22).** the admin API is one same-origin route, TOTP enrolment is gated by `session.enrolCheck`, and the owner turns Supabase TOTP enrolment off after enrolling.
- **Status.** adopted.
- **Sources.** VF-B5, VF-B12, VF-B13; SA-C05, SA-M24, SA-M25.

## D-008 Freshness and rebuild strategy

- **Context.** Spec 12.2 says "at most one build per 10 minutes" but defines no debounce owner, build host or Publish-now authentication. GitHub Free gives 2,000 private minutes a month; scheduled runs can be delayed or dropped; Workers Builds is a second 3,000-minute pool with Deploy Hooks. A 10-minute floor is a ceiling, not a cadence.
- **Decision.**
  - **Production deploys happen only from CI**, never from the laptop. One path: `deploy.yml` with `concurrency: {group: deploy, cancel-in-progress: false}` and a scoped `CLOUDFLARE_API_TOKEN`.
  - **Dirty flag.** `site_state(id=1, dirty_since, last_build_started, last_build_status, last_sync_ok_at, known_video_ids)` and a SQL function `mark_dirty()`. "Public content changed" means a new, removed or hidden video, or an edit to a player, tournament, match or product, or a publish or hide action. Placements, live status, the announcement bar and the sponsor schedule are dynamic and never mark dirty. View-count drift alone marks dirty at most once per 24 hours.
  - **Trigger.** A Cloudflare Worker Cron Trigger runs every 5 minutes; if dirty and at least 10 minutes since the last build start it calls GitHub `workflow_dispatch` (fine-grained token, Actions write on one repo, stored as the Worker secret `REBUILD_DISPATCH_TOKEN`, OT-42). Verified 2026-10-21 (VF-A32): GitHub's "Create a workflow dispatch event" needs only **Actions: write**, whereas "Create a repository dispatch event" needs **Contents: write**, which would also let the token push code. So the trigger is `workflow_dispatch` only and `deploy.yml` has no `repository_dispatch` trigger. The workflow stamps `last_build_started` at start and clears `dirty_since` at the end only if it was not set again during the build.
  - **Publish now** is a Worker endpoint that verifies JWT, role and `aal2` and dispatches immediately (the concurrency group serialises). Hide and takedown actions call it automatically (D-014).
  - **Nightly deploy** at 00:30 IST (`0 19 * * *` UTC) always rebuilds. **Sync** every 6 hours at an off-peak minute (for example `17 */6 * * *`) as the safety net; a sync that changed public content builds and deploys inline.
  - **RSS detector.** A Worker cron every 10-15 minutes fetches the channel RSS, compares video IDs with `known_video_ids` and dispatches sync and deploy on a new ID; it costs no Actions minutes when nothing is new. RSS is best-effort and never fails a sync.
  - **Service-level target (proposed, to be timed with an unlisted upload):** a new public video is live within 45 minutes on 95% of uploads, 7 hours worst case if the detector fails. DoD 3 is reworded to this.
  - **Dead-man switch.** Alert by Telegram and email if there is no successful sync for 8 hours.
  - **Build host.** Default is GitHub Actions. M0 measures real build minutes; if 6-10 builds a day at the measured length would use more than 60% of the 2,000 free minutes, move the production build to Workers Builds (a 3,000-minute pool; the Deploy Hook becomes the single trigger; `.nvmrc` pinned; build variables are not visible at runtime; the secret key never enters the build). The repo stays private.
  - **Rollback and gate.** Roll back with `wrangler versions rollback` or by redeploying the previous commit. Before a new version takes traffic: HTTP 200 on 10 key URLs, the file-count budget (D-009) and the privacy scan; a failing gate keeps the previous deploy live and alerts the owner.
  - **Cron Triggers on Workers Free (checked at G0, verified 2026-10-21, VF-A28).** The Free plan allows **5 Cron Triggers per account** and **10 ms of CPU per invocation** (Paid: 250 triggers; 30 s for a schedule under 1 hour, 15 min otherwise). The two Worker crons above (5-minute dispatcher, 10-15 minute RSS detector) use 2 of the 5 (3 if the dead-man switch also runs as a Worker cron); one cron expression can also serve several jobs if the handler checks the time. The dispatcher and detector must keep parsing tiny (CPU time, not waiting for the network, is what counts; not re-tested). Whether cron runs count toward the 100,000 requests a day is unverified. **Custom Worker entry needed:** the adapter's default entry exports only `fetch`, so the cron milestone (M2a, with the RSS detector) needs a custom entry file that exports `scheduled` and re-exports `fetch` from `@astrojs/cloudflare/handler`, or a second small Worker. This was not tested in G0; decide and test it at M2a. Fallback if crons do not fit: the 6-hourly schedule plus a manual Sync now.
- **Consequences.** A new upload is not instant; minutes are budgeted (D-038); the Worker holds a dispatch token. M0 did not measure build minutes on a GitHub runner (needs the repository and OT-02): the build-host rule above still waits for that measurement.
- **Amended by D-065 (2026-10-21).** `deploy.yml` runs only the strict build, and only from `main`.
- **Amended by D-085 (2026-10-22).** the cron entry is built but parked behind `features.youtubeApiData`.
- **Status.** adopted.
- **Sources.** VF-A15, VF-A16, VF-A18, VF-A25, VF-A28, VF-A32; SA-C11, SA-M04, SA-M08, SA-N22; `docs/G0_RESULT.md` step 7.
- **Amended by D-097 (2026-10-22).** the Worker Cron Trigger (5-minute dirty-flag poll, RSS detector) and `wrangler versions rollback` do not exist on Vercel. Cron is Vercel Cron (Hobby daily only; Pro per minute) or a GitHub Actions `schedule:`; rollback is Vercel Instant Rollback or redeploying a commit. See D-097 and the worker notes in `docs/m3/`.

## D-009 File-count and Workers Free budgets

- **Context.** Workers Free allows 20,000 static files per version and 100,000 requests a day; every form post, `/go` click, beacon and admin call is a billable request; Pagefind adds a file per indexed page; Satori and resvg exceed 10 ms CPU.
- **Decision.**
  - CI counts **regular files in `dist/client`** (the upload set; not folders, not `dist/server`): **warn at 10,000, fail above 14,000** (70% of the cap). Thresholds are unchanged by the G0 findings below. `_redirects` is generated at build with chains collapsed and fails above 1,800 lines (Bulk Redirects beyond); `_headers` stays under 100 rules and middleware sets headers on Worker responses.
  - Posters, creatives, sponsor logos and any P2 OG images come from Supabase Storage (public bucket) or R2, never `dist/`; thumbnails stay on `i.ytimg.com`.
  - P1 uses one branded default OG image. P2 OG images are English-only or rendered at build time in CI and uploaded; they are not rendered per request on Free (about 500 ms CPU measured; Satori's Tamil rendering issue is open); a render test on real Tamil titles comes first.
  - Request budget: one batched beacon per pageview; cache `/api/placements` and live status at the edge; log `/go` clicks with `ctx.waitUntil`; build PDFs in CI or in the browser (print CSS); each endpoint at most 2-3 subrequests; an alert at 70% of the daily quota; Workers Paid is the first paid upgrade (rule in D-036).
  - Build memory: one data snapshot `.cache/snapshot.json` loaded once (no per-page network calls); `NODE_OPTIONS=--max-old-space-size=4096` locally and 6144 in CI. At G0 this was never needed (15,000 pages peaked at 754 MB with `node` prerender and 1,455 MB with `workerd`); keep it as a guard.
  - **Measured file-count facts (G0, verified 2026-10-21; VF-A28, `docs/G0_RESULT.md`).** 15,000 prerendered pages produce 15,010 files in `dist/client` (about 1.0007 files per page): 75% of the Free plan's 20,000-file limit and **above this record's own fail line of 14,000**. 8,000 pages give 8,010 files (40%). Wrangler's "Read N files" line also counts folders (30,012 for the 15,000-page build), about double the real asset count, so it must not be used as the gate. **The file budget is therefore effectively a page budget:** one page is one file, plus about 10 other files, and the one JSON search index (D-010), fonts, `_astro` assets, sitemaps and favicons share what is left below the fail line. The real catalogue is about 1,900 videos and D-012 and D-013 limit player pages to adult-confirmed players, so the expected count is far lower than the 15,000-page stress test; it must still be watched as player and tournament pages are added (M2 profiling gives the first real number). If the planned total nears 14,000, trim pages (the D-013 tiers) or take Workers Paid (100,000 files, D-036). Thresholds unchanged.
- **Consequences.** No per-item images in the bundle; thin endpoints; the page count is the lever that moves the file count.
- **Amended by D-066 (2026-10-21).** The first-party JavaScript budget is defined ("on view", strict, 81,920 bytes gzip) and checked in CI and in the strict build; the file-count thresholds are unchanged and are enforced by the release check (D-065).
- **Status.** adopted.
- **Sources.** VF-A10 to VF-A14, VF-A17, VF-A24, VF-A28; SA-M01, SA-M11, SA-M52.
- **Amended by D-097 (2026-10-22).** the Workers Free 20,000-file cap and 100,000 requests a day are gone. Vercel has no upper limit on build output files; build time (45 minutes) is the constraint. The 10,000 warn / 14,000 fail file budget stays as a soft guard on build time and page count.

## D-010 Search design

- **Context.** Spec 12.1 says Pagefind powers search. Pagefind writes one fragment file per indexed page, its fragment-grouping change is unmerged, and protected players must never be searchable.
- **Decision.** P1 search is one pre-built client-side JSON index (MiniSearch or Fuse, chosen at M2) of public `adult_confirmed` players (display name, `name_normalized`, `latin_key`) and tournaments; its size (the audit estimates 300-500 KB) is unmeasured. Protected and unknown-age players never enter it. `/matches` filters from one JSON of public matches that also excludes protected matches. Pagefind is used only for tournament and match pages **if** the M0 and M2 file counts leave headroom, with a `data-pagefind-body` allow-list and `data-pagefind-ignore="all"` on protected blocks. A CI test loads the built index and asserts that no protected name or slug appears. Zero-result queries are logged under the privacy rules (D-028). Cloudflare Turnstile (D-029) loads on first interaction with a form, not on page load, so no third-party script sits on the page-load path; the JS budget counts first-party JS, measured by a size check (SA-N01).

- **Amended by D-066, D-047 and D-052 (2026-10-21).** The JavaScript budget is measured "on view" by `scripts/check-js-budget.ts` (D-066); Turnstile test secrets need an explicit switch (D-047); Turnstile loads on first interaction with a form (D-052).
- **Status.** adopted.
- **Sources.** VF-A12, VF-A13; SA-M01, SA-N01.

## D-011 Backups and restore

- **Context.** Supabase Free has no automatic backups. The direct database host is IPv6-only and GitHub runners are IPv4; the runner ships a PostgreSQL 16 client while new projects are on 17; `supabase db dump` skips `auth` and runs in a container; Storage files are not in backups; dumps contain all personal data.
- **Decision.**
  - `backup.yml` runs weekly (spec), plus an extra dump before every backfill, reparse apply or risky migration. When Supabase Pro starts, its daily backups add a second layer.
  - Plain `pg_dump --format=custom --no-owner` of the whole database including `auth`, through the **session-pooler URI** in `SUPABASE_DB_URL` (port 5432, user `postgres.<project-ref>`), with `postgresql-client-17` installed (confirm the server major under Project Settings > Infrastructure) and a read-only database role where possible.
  - Encrypt with `age` to a public key committed to the repo; the owner keeps the private key offline (sealed copy plus one trusted escrow). Plaintext dumps are never stored.
  - Store as a GitHub artifact with 56-60 days retention in the private repo **and** an off-GitHub copy (the owner's Google Drive; R2 only if the owner accepts adding a card). P1 does not depend on R2.
  - Back up Storage objects separately by listing and downloading through the Storage REST API with the secret key (the S3 route is unverified on Free).
  - Alert on failure and when the newest backup is older than 9 days.
  - **Restore drill (DoD 10), in two parts so the private key never goes online.** (1) **Automated, in CI:** `restore.yml` takes a dump of the **dev** project (made-up data only), encrypted with a separate **drill-only** `age` key pair whose private half is a GitHub secret (it can decrypt made-up data and nothing else), restores it into a Postgres 17 service container, applies `erasure_log`, and asserts row counts, RLS and grants. This proves the restore pipeline on every run. (2) **Manual, once before G3 and after any major schema change:** the owner and Claude restore the **latest real production dump** together at the owner's PC, unlocking it with the owner's offline private key, into a throwaway local PostgreSQL 17 install that Claude asks about first (size and install steps confirmed before asking); the throwaway database and the decrypted file are deleted afterwards and the result is logged. No scratch Supabase project is used (the Free cap is two). The production backups are never decrypted in CI. Supabase-specific restore compatibility (auth and storage role ownership) is untested and kept as a documented residual risk; break-glass is a new project, restore `public`, recreate admin users.
- **Consequences.** The owner must keep the private key safe; restore of `auth` into a Supabase project may need manual steps. DoD 10's "one restore tested" is met by the automated drill (pipeline) plus one manual real-data drill before G3 (data). The manual drill installs software on the owner's PC, so Claude asks first (BUILD_PLAN section e item 9).
- **Amended by D-072 (2026-10-21).** Backup workflow details: the dump is piped into `age` with no plaintext file, and the database password never appears on a command line.
- **Status.** adopted; the manual real-data restore drill needs the owner's approval at M4 (software install on the PC).
- **Sources.** VF-A19, VF-A20, VF-B3, VF-B10, VF-B14; SA-M07.

## D-012 Protected-player (junior) default

- **Context.** DPDP s.9(1) needs verifiable parental consent before processing a child's data and s.9(3) bars tracking and targeted advertising directed at children (binding about 2027-05-13); no exemption fits a sports publisher; legacy children's data is not grandfathered. Spec 15.3's boolean `is_junior` fails open because legacy titles have no age token. The channel's archive makes "unknown age" the majority case. A lawyer's opinion is needed; until then the protective option is the default.
- **Decision.**
  - `players.age_status` is an enum: `adult_confirmed`, `minor_confirmed`, `minor_suspected`, `unknown` (default `unknown`), with `age_signal text[]` recording which rule fired. Signals: age tokens (U-8 to U-19, Sub Junior, Junior, Youth, Cadet, Mini, Under or Below n), BS/GS/BD/GD, tournament level school_college, appearing in a tournament whose categories include an age group, any unmapped age-like word (UNKNOWN_AGE_TOKEN, fail closed). U-21 is not an age signal.
  - **Protected = every status except `adult_confirmed`.** Only an admin review (bulk action) or a verified claim sets `adult_confirmed`; a self-claim alone never lifts a flag. Splits inherit the status; merges take the more restrictive status and are blocked between a minor status and `adult_confirmed` without a logged override.
  - **Protected treatment**, enforced in the `api` view SQL and by a page-level layout flag, with tests: no player profile page; the name appears only as plain text where it occurs; noindex (meta and `X-Robots-Tag`); absent from sitemaps, search and JSON indexes, directory, A-Z, trending, related lists, OG images and every other player's page; no sponsor banner, impression beacon, events, Follow, affiliate link or prefilled share text naming the child; no search-query logging; neutral court graphic instead of the thumbnail on the facade; opaque slugs with no district; matches carrying a **real minor signal** are held in review rather than auto-published.
  - Two settings control protected match pages without code changes: `unknown_match_mode` and `minor_match_mode`, each `noindex_minimal` (page exists, noindex, raw YouTube title, no parsed player links) or `hidden`. **Recommended launch values:** `noindex_minimal` for `unknown`, `hidden` for `minor_suspected` and `minor_confirmed` until a parent opts in (D-015). The owner and the lawyer confirm before the launch gate.
  - M0 reports counts per status so the owner sees the size of the job; the owner's priority adult list (spec input 14) is bulk-confirmed to reduce `unknown`.
  - **Legacy content is not assumed to stay.** The lawyer opines on legacy children's data; plan either a parent-contact and consent backfill or a pre-2027-05-13 policy to blur, unlist or retitle junior-identifiable items; the site cannot recall copies on YouTube, caches or WhatsApp.
  - Owner guide: do not tag or message junior players' own accounts for promotion; any future event registration for juniors comes through a parent (P3).
- **Consequences.** Far fewer player pages and less SEO at launch; owner effort to confirm adults; the "pages indexed" target is re-based (D-013).
- **Amended by D-076 and D-078 (2026-10-22).** the owner confirmed the recommended launch values; an unknown-age player gets a nameless minimal noindex page; the lawyer confirms before launch.
- **Status.** proposed - needs owner approval (owner and lawyer).
- **Sources.** VF-E1 to VF-E5, VF-E19; SA-C01, SA-M21, SA-M31.

## D-013 Player identity tiers and which pages exist

- **Context.** First-name-only names (GANESH, SANTHOSH) identify dozens of people; exact-alias matching would merge them; public pages for thin or wrong identities are SEO and privacy liabilities.

A player profile page is generated only when the player is `adult_confirmed` **and** (has a confirmed alias **or** appears in at least 3 matches across at least 2 videos with consistent context) **and** is not provisional. Everyone else appears as plain text on match pages. A tournament page exists when at least 3 matches share a (`series_key`, `edition_year`) or the owner promotes it. ## D-014 Takedown: suppression, tombstones, emergency hide

- **Context.** Hiding is not removal: static copies persist, sync re-creates deleted rows, redirects keep old names, YouTube is untouched. IT Rules timelines changed in February 2026.
- **Decision.**
  - A **suppression table** keyed by normalised name, `youtube_id` and `player_id` is checked by sync, reparse, merge and backfill before any insert. Hidden entities are tombstoned, never hard-deleted.
  - **Emergency hide** (one admin action, RPC): (1) set the flag, (2) deploy immediately through Publish now, (3) purge Cloudflare cache for the affected URLs, (4) delete the entity's `slug_redirects` rows and serve 410, (5) show the owner a checklist: set the YouTube video private or unlisted, file a Google Search Console Removals request. An edge kill switch hides the top-visited paths while a rebuild runs. For minors, auto-hide on receipt (reversible), then verify.
  - Timestamps (received, hidden, live copies gone) prove the service level. A named deputy (a trusted person reachable by WhatsApp) covers owner absence.
  - Timelines in the policy: acknowledge within 24 hours; resolve within 7 days; act on a court order or reasoned government notification within 3 hours (the owner's phone must be reachable); minors' hide or removal request target 48 hours (stricter than DPDP's 90-day outer limit). Whether Power Smash is an intermediary for any feature is a legal question; these are adopted as operating targets either way.
  - `/content-removal` says what Power Smash will and will not do (remove from the site, set YouTube videos private; copies outside its control cannot be recalled).
  - No public user-generated content (comments, direct upload, reviews) in Phase 1.
- **Consequences.** More moving parts in the hide path; the owner must keep the phone reachable.
- **Amended by D-062 (2026-10-21).** The response times on the public Content Removal page are stated as targets, not guarantees.
- **Amended by D-080 and D-081 (2026-10-22).** step 4 serves a 301 to a neutral noindex page because `_redirects` has no 410; a Worker for real 410s is proposed.
- **Status.** adopted (the 3-hour and 7-day figures come from third-party summaries of the 2026 amendment; LAWYER confirms).
- **Sources.** VF-E6, VF-E9; SA-C02.
- **Amended by D-097 (2026-10-22).** step (3) "purge Cloudflare cache" no longer applies: the site is served by Vercel. After Publish now, confirm the old address on a phone; how long Vercel keeps cached copies of the previous deployment is unverified (not covered by VF-V1 to VF-V8). Search Console removal still applies.

## D-015 Claim, removal and parental-consent verification

- **Context.** "Verified by phone or WhatsApp" names no record to verify against; Rule 10 illustrates verification with held identity data or a DigiLocker-style token; a phone declaration is not an enumerated method.
- **Decision.**

## D-016 YouTube Developer Policy mitigation

- **Context.** This is the top risk. III.E.4.h bans creating "new or derived data or metrics" from API data; the guide says title and thumbnail must be unmodified; non-authorized statistics cannot be stored beyond 30 days; III.G.1.d limits sponsorship on pages containing API data; III.G.1.c bars ads on or in the player; III.F.3 bars charging to watch. No text says whether parsing titles into player and tournament pages is permitted. Enforcement is quota reduction or termination.
- **Decision.**
  1. **Written clarification.** Claude drafts a short query (`docs/YOUTUBE_POLICY_QUERY_DRAFT.md`): the site is an archive of the owner's own channel; titles are parsed by Power Smash into its own player and tournament records, labelled as Power Smash data; no composite scores; sponsor slots on pages with independent content. **The route (checked 2026-10-20 and 2026-10-21):** the only official linked form found is the "YouTube Data API Services Audit and Quota Extension Form" (https://support.google.com/youtube/contact/yt_api_form), which YouTube's Developer Policies Guide points to for developers unsure about compliance. There is no dedicated "policy question" form and no published response time. The owner submits the query from the channel's Google account, chooses the compliance-audit option, and says in the first line that it is a policy-interpretation question and not a quota request; the reply is stored in `docs/`. The reply may be an audit questionnaire or a general pointer rather than a clean yes or no. The answer is **not assumed**.
  2. **A design that survives "no".** The match, player and tournament records are Power Smash's own curated records keyed by video ID; the API supplies only thumbnail, duration, views, embeddability, live status and title text. Option B to evaluate with YouTube's reply: ingest titles for parsing from an owner-provided YouTube Studio or Takeout export plus RSS for new uploads (not API data), keeping the API for rendering fields.
  3. **Display rules.** Show the raw YouTube title unmodified on every match page (and carry or link it on cards); `VideoObject.name` is the raw title; parsed fields are labelled "Match details by Power Smash" with a sentence on the legal page; per-video views are shown exactly as returned and labelled "YouTube views"; lists sorted by YouTube views are acceptable; no composite score and no per-player aggregate views.
  4. **Trending players** (spec 7.1) is replaced by a non-view-based "Recently added" rail built from the site's own data (D-035); `video_stats_daily` is not built.
  5. **30-day rule: refresh before day 30 or delete the stored value; hiding is not enough.** Policy III.E.4.d lets data fetched with a plain API key be stored "not longer than 30 calendar days", after which it must be refreshed or deleted (VF-C3). So: `api_fetched_at` on every video; alert at 14 days stale; hide API-derived fields from display at 28 days as the visible safety margin; **and** a nightly purge deletes (nulls) any stored API-derived value that has not been refreshed within the window, with its threshold set below 30 days (for example 29) so a nightly run never leaves a value past day 30. Hiding a value that is still stored does not meet the rule. Weekly refresh detects removed or private videos; no statistic (including subscriber count) is kept more than 30 days: `channel_stats` holds at most 30 days and is purged nightly; long-term KPIs come from the owner's monthly entry or Studio export labelled "as of". Whether Power Smash's own parsed records count as stored API data under this clock is asked in the query (draft Part B, question 4); if YouTube says yes, the same refresh-or-delete clock applies to them.
  6. **Sponsors.** Slots sit beside, never over or inside, the player; sponsor slots appear only on pages with substantial site-original content (tournament pages, adult player pages with real content); a match-page banner shows only when the page passes an independent-value rule and is off by default; the paid HD file is the owner's own original footage delivered separately; watching is never gated.
  7. **Embed rules.** Unmodified `i.ytimg.com` thumbnail at least 120x70; one tap starts playback (test on iOS Safari); no overlays; `Referrer-Policy: strict-origin-when-cross-origin` on all pages, never `no-referrer` or `same-origin`, and no `noreferrer` on YouTube links; CSP `frame-src` allows `https://www.youtube-nocookie.com`; store `embeddable`, `madeForKids`, `ytRating` and `regionRestriction` and fall back to "Watch on YouTube".
  8. **Legal text.** The privacy policy states that the site uses YouTube API Services, links the Google Privacy Policy and the YouTube Terms, and says users of video features agree to be bound by the YouTube Terms; no specific cookie behaviour is claimed without a browser test.
  9. **Pre-launch.** Re-read the Developer Policies (updated 2026-10-15) and the API revision history; repeat quarterly.
  10. **Residual risk.** The owner either waits for YouTube's reply or explicitly accepts the residual risk before the public archive launches.
  11. **Content-category inference (risk detail, added 2026-10-21).** YouTube's Developer Policies Guide lists inferring or estimating a video's content type or category as something not to do (VF-C4). D-033 classifies every video as match, short, live or other from title patterns, duration and playlist membership, which is that kind of inference, and D-016 item 1's query is therefore also asked about it (draft Part B, question 1). It is not cleared and must not be treated as cleared: when YouTube replies, the owner and Claude decide whether the classification stays as built or changes (the draft's Part D lists the consequences of each answer).
- **Consequences.** Trending is removed; match banners are conditional; fewer derived statistics; the launch gate depends on the owner's decision. The nightly purge in item 5 is a build item (M2), not a display setting.
- **Amended by D-059 (proposed) and D-061 (2026-10-21).** Item 5's 30-day clock is applied to API data, and owner-stated "as of" figures are shown with a date and a staleness check (D-059); the legal wording of items 3 and 8 is held back until the features exist (D-061).
- **Amended by D-081 (2026-10-22).** statistics are nulled at 28 days and rows retired at 29 days, to leave margin before day 30.
- **Status.** proposed - needs owner approval.
- **Sources.** VF-C3 to VF-C9, VF-C25, VF-C26; SA-C12, SA-M05, SA-M48; `docs/YOUTUBE_POLICY_QUERY_DRAFT.md`.

## D-028 Privacy, consent, retention, logs and breach architecture

- **Context.** The spec says "design to the principles of DPDP". DPDP duties bind about 2027-05-13 but the SPDI Rules and IT Act s.43A apply now and the CERT-In directions bind today.
- **Decision.**
  - A notice on every form; `notice_versions(id, kind, language, full_text, sha256, effective_from)`; an append-only `consent_events` table (subject, purpose, notice version, given or withdrawn, time, ip hash, channel); consent per purpose; a suppression list of hashed emails and phones; the Tamil notice reviewed by a native speaker.
  - The privacy policy is live at launch (SPDI Rules), names every processor and country (Cloudflare, Supabase, Resend, Telegram, Razorpay, YouTube and Google, GitHub), a named data contact, the grievance officer, and a 90-day maximum response commitment. It states that data collected before 2027-05-13 is in scope when the duties start (re-check the Gazette).
  - **Retention schedule** (also in RUNBOOK): closed leads anonymised after 24 months; tax and accounting records as the CA confirms; `payment_events` keeps only signature-valid payloads and redacts contact fields after 90 days; raw `events` and `outbound_clicks` 90 days then daily aggregates; `profile_requests` until resolution plus 12 months with details redacted afterwards; audit diffs redact PII from the start; the backup retention window is stated; event documents 30 days after the event (P3). An `erasure_log` (hashed identifier and date) is re-applied after any restore.
  - **Logs:** keep 180 days of access and admin-action logs with a copy held in India (CERT-In) and plan one 12-month policy that also covers the DPDP one-year floor; sync clocks to NTP; which Cloudflare or Supabase logs count is a lawyer or security-adviser question.
  - **Breach runbook:** what counts as a breach; first-hour steps (rotate keys, revoke sessions, disable forms, preserve logs); the CERT-In 6-hour report; from 2027-05-13 the same-day notice to affected people and the 72-hour report to the Board; contacts; English and Tamil templates; Telegram alerts on role changes, CSV exports, UPI or WhatsApp setting changes and failed-MFA bursts.
  - Search queries are normalised and truncated to 40 characters with digit runs of 6 or more and email-like strings dropped, and are not logged on protected pages; analytics events are schema-validated. Cloudflare Web Analytics needs no banner; no Google Analytics or Meta pixel without a banner and a policy update. Avoid collecting sensitive data (passwords for public users, health or injury details, card data).
  - **Video facade notice.** The click-to-load video facade shows a visible one-line notice, "This loads YouTube", before the iframe loads (SA-N09); the privacy policy also names the YouTube iframe, `i.ytimg.com` and Turnstile.
- **Consequences.** More tables now; evidence of consent exists when the duties start.
- **Amended by D-050 and D-044 (2026-10-21).** The consent tables exist (migration 0002) but the suppression list, `erasure_log` and withdrawal flow are not built yet (D-050); the retention job is not built and must run before the first record reaches the stated age (D-044, D-061).
- **Status.** adopted (legal texts reviewed by a lawyer before launch).
- **Sources.** VF-E1, VF-E6 to VF-E8, VF-E17; SA-M22, SA-M23, SA-M26, SA-M28, SA-N09.

## D-029 Security baseline

- **Context.** The spec names controls without mechanisms; Worker responses are not covered by `_headers`.
- **Decision.**
  - **Headers and CSP** through `_headers` plus Astro middleware: a CSP with `default-src 'self'`, script hashes, `frame-src https://www.youtube-nocookie.com https://challenges.cloudflare.com`, `img-src 'self' data: https://i.ytimg.com`, `connect-src` for the Supabase URL; HSTS (preload after testing); `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; a restrictive Permissions-Policy; `frame-ancestors 'none'` on the admin; `X-Robots-Tag: noindex` on the admin, `/api`, `/go` and non-canonical hosts. Sponsor creatives are static images only.
  - **Forms:** Turnstile `siteverify` with hostname and action checks; the Workers Rate Limiting binding plus a database counter per email and phone; a 20 KB body cap; honeypot and minimum fill time; one confirmation mail per address per 24 hours with 128-bit tokens that expire in 24 hours; a client idempotency key with a UNIQUE constraint; auto-acknowledgement carrying only the reference and a sanitised first name; CR and LF stripped from header values; identical responses for new and existing subscribers; generic errors with a correlation id and a WhatsApp fallback.
  - **Input:** https-only URLs with the host checked, strict handle patterns, length caps, control characters stripped; a safe JSON-LD serialiser (escape less-than, greater-than, ampersand, U+2028, U+2029); no raw HTML (lint ban on `dangerouslySetInnerHTML` and `set:html`); external user links get `rel="noopener noreferrer nofollow ugc"`.
  - **YouTube descriptions** are never rendered raw: a templated or at most 200-character redacted text with phones, emails and URLs stripped.
  - **Uploads:** magic-byte typing (JPEG, PNG, WebP only), re-encode to strip EXIF, 5 MB enforced in the Worker, UUID names, a private pending bucket copied to the public bucket on approval, no anonymous list policy, an alert at 70% of storage.
  - **Hashing:** HMAC-SHA-256 with a Worker-only key and key id, a random daily secret with a 48-hour TTL for session hashes, output truncated, documented as pseudonymous.
  - **Exports and files:** CSV cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading quote; exports are owner-only with `aal2`, audit-logged, announced on Telegram and limited to needed columns; `.ics` fields are escaped and folded per RFC 5545.
  - **Alerts:** Telegram text is plain (no parse mode), contains type, reference, first name or initials, district and a deep link only, and goes to a private 1:1 chat; junior-related requests send "new profile request {ref}" only.
  - **Privacy scan:** redaction first, scan second; scan HTML, JSON, `.ics` and decoded search output with explicit patterns and an allowlist of official contact values (all formats) and per-page consented contacts; on a hit the previous deploy stays live, Telegram alerts and an "exclude the page and deploy" path exists. Organizer contacts appear only through a click-to-reveal edge endpoint, never in static HTML.
  - **Logs:** redacted structured logs only (reference, status, no bodies, no phone or email, no tokens), short retention, lint against logging request objects.
- **Consequences.** More work in M1, but it is the foundation for every form.
- **Amended by D-045 (proposed), D-044, D-063 and D-064 (2026-10-21).** The default alert has no district and no link containing the customer's phone (D-045); limits and a global flood breaker (D-044); the CSP is built from build-time hashes into a generated `_headers` (D-063); the privacy scan reads decoded text (D-064).
- **Status.** adopted.
- **Sources.** VF-A14, VF-C7; SA-M06, SA-M12 to SA-M14, SA-M16 to SA-M18, SA-N07, SA-N08.
- **Amended by D-097 (2026-10-22).** the Workers Rate Limiting binding does not exist; the database counter and global caps (D-044) carry the limits, optionally with Vercel WAF rules. Headers come from `vercel.json` plus middleware, not `_headers`. Turnstile is unchanged.

## D-031 Sponsor placement delivery and tracking integrity

- **Context.** Baking a schedule into pages contradicts "no rebuild lag"; counts are easy to inflate; sponsor trust is the revenue.
- **Decision.** No placements in the HTML. Each page has a reserved-size slot and a script of about 1 KB that reads `/api/placements` (one global JSON; Worker plus Cache API, `s-maxage=300, stale-while-revalidate=600`; the admin edit purges it). Slots as in spec 8.3 with the guardrails (one banner above the fold at most, never inside the player, no pop-ups); paid slots are labelled "Sponsored" or "Ad" and the home and footer strip "Partners" with context. `/go/[slug]` resolves slugs from the database only; unknown, expired or paused slugs return 404 or go to `/partner`; the target must be https on the sponsor's registered domains; UTMs are appended correctly to URLs with queries or fragments; robots disallow `/go/`; links carry `rel="sponsored nofollow"`. Bots are flagged at ingest (user-agent list plus a missing JS signal) and stored as `is_bot`; impressions are deduplicated per ip hash per window; an impression means the slot is at least 50% visible for 1 second (IntersectionObserver), sent in one batched beacon on pagehide, signed with a per-build token and rate-capped, with `page_path` checked against the route allowlist; counters use an atomic `bump_stat(placement_id, date, impressions, clicks)` upsert; raw rows are kept 90 days; the partner report (CSV in Phase 1) notes that ad blockers cause under-counting. Protected pages carry no placement and no beacon. A match-page banner appears only when the page passes the independent-value rule (D-016). If M3 slips, the fallback is Cloudflare Web Analytics page counts plus the server click log (D-035).
- **Consequences.** Sponsor numbers are defensible.
- **Amended by D-089 (2026-10-22).** path gate, user-agent-free dedupe, fail-closed limiter and go-link host check.
- **Status.** adopted.
- **Sources.** SA-M02, SA-M19.

## D-033 YouTube sync design details

- **Context.** The spec's classification and quota assumptions were partly wrong (VF-C1, VF-C10, VF-C11).

## D-042 Lead endpoint: order of checks, idempotency, reference codes and stored data

- **Context.** Milestone M1 built `POST /api/lead` (spec 7.x, 8.1, 11.2; D-025 random `PS-YYYY-` references; D-029 form rules). A Turnstile token works once (a replay returns `timeout-or-duplicate`, TP-A2.2), so a retry cannot re-verify it. The three M1 reviews (security S-, correctness B-, conformance C-) changed the order and added limits; this record is the merged result. Field-level rules are in D-048, failure handling in D-043, limits in D-044, alert content in D-045.
- **Decision.**
  - **Order of checks:** method, same-origin `Origin`, content type (415), body cap of 20 KB read as a stream and cut at the cap (413), JSON (a top-level value that is not an object is a plain 400, B-3), validation (422), honeypot and fill time, configuration check, per-connection limit, **idempotency lookup**, global flood breaker, Turnstile (fail closed), per-phone and per-email limits, insert, owner alert, response. `POST /api/event` reads its body the same way (S-3).
  - **Idempotency before Turnstile.** The same `idempotencyKey` with the same contact returns the same `ref` (HTTP 200, `replay: true`) without a new siteverify call, row or alert; the same key with a different contact is `duplicate` (409); two identical requests racing are settled by the `leads_idempotency_key_uq` constraint.
  - **Reference code** `PS-<IST year>-<6 characters>`: 30 random bits from `crypto.getRandomValues`, Crockford base32 without I, L, O, U, never sequential; a collision on `leads_ref_code_uq` retries with a new suffix (up to 4 times).
  - **Stored:** the contract fields in `leads`, kind-specific fields in `payload` jsonb, consent id, version and time, a pseudonymous connection hash (D-044), `alert_state`. Never the raw IP, the Turnstile token or the request body. A trigger writes the `created` row of `lead_events`. Logs are JSON lines with only outcome, error code, kind, reference, correlation id and HTTP status; a test spies on every `console` method and asserts no personal value appears.
  - **A tournament listing with the coverage box ticked** also creates a linked coverage lead (own reference, deterministic idempotency key, `parent_lead_id`); the owner is alerted once for both. `leads.type` accepts `tournament_submission` (not in spec 11.2) until the M3 tournament queue exists.
  - **Consent version** is stored as the form supplies it if it matches `^[A-Za-z0-9._-]{1,40}$` and the id is `lead-notice`: a tab opened before a wording change must not lose a lead.
  - **Honeypot** field `website`: a hit returns a normal success with the WhatsApp link and stores nothing (browser autofill can fill a hidden field; a real person still gets a way to reach us).
  - **Fill time:** the client-reported `elapsedMs` below `MIN_FILL_MS` (1,000 ms) answers `rate_limited` (a retry works); an absent value means no check; the server clamps the value (D-048).
  - **Coverage `startDate` is optional in the contract** (loosening a contract later breaks callers, tightening does not) while the forms require it (D-025, D-053).
  - Every API response is `no-store` and `noindex`. The Telegram text is plain with no parse mode (D-029). Telegram is retried once on a network error or a 5xx; a 429 is not retried (one chat, lead volume, the email channel covers it, and a wait would add latency inside the visitor's request).
- **Consequences.** `docs/m1/leads-api.md` is the reference for the form code; contract changes are additive only. CPU time against the Workers Free limit of 10 ms is **not measured**: a stored lead makes about 18 subrequests (counters 2, lookup 1, global 1, siteverify 1, contact counters 4, insert 1, evidence and hit writes 5, alert 1, alert state 2; about 22 with email on, about 25 for a tournament listing with the coverage box and email); the limit is 50. Measure CPU in Workers Logs on the first preview deploy; if it is tight, drop the database connection counter and rely on the Rate Limiting binding (D-044).
- **Status.** adopted.
- **Sources.** `docs/m1/leadbackend-notes.md` sections 2 and 3 (deviations 5 to 12); `docs/m1/leads-api.md`; `docs/m1/fix-backend-notes.md` (S-3, S-6, B-3, B-4, section 7); TP-A2.2 and TP-A7 in `docs/m1/third-party-integration-facts.md`.

## D-043 Failure modes: nothing is lost silently, the visitor can always reach the owner

- **Context.** Spec 12.7 and D-029 ask for no silent loss and a WhatsApp fallback. Cloudflare's Turnstile can be unreachable; the database or Telegram can fail.
- **Decision.**
  1. **The database cannot store the lead** (insert fails, database down, secret missing): HTTP 503 `degraded` with the WhatsApp link, a provisional reference quoted in the WhatsApp text and a correlation id. The owner is alerted (Telegram, and email if on) with `LEAD NOT SAVED (database problem)`, only after Turnstile passed so a spammer cannot trigger it; content per D-045. If Telegram is also down a `degraded_unalerted` log line records it. Not a fake success: the visitor must not believe a stored enquiry exists.
  2. **The database is fine but the alerts fail:** the lead is saved and the visitor sees success; the row gets `alert_state = 'failed'` (indexed) and a `lead_events` row `alert_failed`; email is an independent second channel, so a lead is `failed` only if every configured channel failed. A job that re-sends alerts for rows with `alert_state <> 'sent'` is **not built** (M2a); until then the owner finds failed alerts in Supabase Studio.
  3. **Rate-limit counters unavailable:** fail open (a lead is not blocked); the insert then shows whether the database is really down.
  4. **Turnstile unreachable, wrong, missing secret, hostname or action mismatch:** fail closed (`turnstile` code, WhatsApp link included); nothing stored, nobody alerted.
  5. **Unconfigured endpoint** (no Supabase URL, Turnstile secret or `HMAC_KEY`, or a refused value): `degraded` with the WhatsApp link, no alert; `/api/health` reports not ready (D-067).
  6. **Forms:** a build without `PUBLIC_TURNSTILE_SITE_KEY` renders no form (the page shows "This form is not switched on yet" and the WhatsApp button, and prints a `TODO(owner)` so the strict gate fails); a development build shows a dev-only notice and the server decides. A form never silently skips the check.
  7. **Retry rule in the browser:** only "no answer at all" (network error, timeout) is retried automatically, once, with the same body and key (safe because the server reads the key before the token). Any answer, `degraded` included, is final for that attempt: the widget is reset, the visitor sees the real message with the WhatsApp fallback and sends again with a fresh token and the same key (B-5).
- **Consequences.** The owner may receive an alert for a lead that is not in the database and must reply on WhatsApp; the "not saved" alert is not de-duplicated against a retry that later succeeds (the reference differs). Keeping the typed data on every failure is part of the contract.
- **Status.** adopted.
- **Sources.** `docs/m1/leadbackend-notes.md` P1 and section 2; `docs/m1/research-notes.md` proposal 3; `docs/m1/forms-notes.md` P4; `docs/m1/fix-forms-notes.md` B-5; `docs/m1/fix-backend-notes.md` P-F2.

## D-044 Rate limits, flood breaker, hashing and growth control

- **Context.** D-029 asks for the Workers Rate Limiting binding plus a database counter. Review S-6 showed that per-IP, per-phone and per-email limits do not stop a distributed flood or plus-aliased addresses; B-6 showed that failed attempts used up a visitor's allowance; S-7 showed unbounded table growth. India's carrier NAT puts many people behind one IP, so the IP limit is generous.
- **Decision.**
  - **Limits (engineering defaults, not business facts; constants in `src/lib/security/ratelimit.ts`):** per connection (HMAC of the IPv4 address or the IPv6 /64) 20 an hour in the database counter, plus the optional Workers Rate Limiting bindings `LEAD_RATE_LIMITER` and `EVENT_RATE_LIMITER`; per phone 3 an hour and 8 a day; per email 3 an hour and 8 a day; one acknowledgement mail per address per 24 hours; counter rows older than 2 days purged opportunistically. `POST /api/event` has no Turnstile: 60 a minute per connection hash per isolate plus the binding.
  - **Global circuit breaker:** at most `LEAD_GLOBAL_HOURLY_CAP` (default 40) accepted enquiries an hour across all visitors; checked after the idempotency lookup and before Turnstile (a flood costs no siteverify calls, a replay of a stored enquiry still works); counted only when a lead was stored. When it trips: 429 `rate_limited` with the WhatsApp link and one "FLOOD PROTECTION IS ON" notice to the owner per hour (no visitor data).
  - **Email key** folds `+tag` everywhere and dots for gmail.com and googlemail.com; used for the per-email limit and the once-a-day acknowledgement.
  - **Accounting:** the phone, email and global hits are recorded only after the lead row was stored, so three degraded failures no longer lock a visitor out; the connection hit is per attempt. `retryAfterSec` is the real wait.
  - **Hashing:** HMAC-SHA-256 with `HMAC_KEY` = `<key id>:<random secret of at least 32 characters>`, output `kid.<32 hex>` (128 bits), documented as pseudonymous (D-029).
- **Consequences.** A real rush above the cap is sent to WhatsApp for the rest of the hour (the owner is told); tune the numbers after real traffic. Without them a patient attacker, bounded by the 100,000 requests a day of Workers Free, could fill the 500 MB Supabase Free database and make every lead degrade to WhatsApp.
- **Status.** adopted.

## D-047 Turnstile test keys work only with an explicit switch

## D-048 Validation: shared rules, client and server parity

- **Context.** The zod contract adds about 30 KB gzip to each form page, which React already leaves little room for (D-066). Reviewers found real input rejected (B-1 pasted phone numbers, B-2 common characters in event names), a date window missing (B-18), `elapsedMs` rejecting whole requests (B-4) and client and server disagreeing (B-13).
- **Decision.**
  - **The server is the authority and validates with zod** (`src/lib/contracts/lead.ts`). The browser does not ship zod: it validates with `src/lib/forms/rules.ts` over zero-dependency shared primitives in `src/lib/contracts/lead-constants.ts` (character patterns, limits, `normalisePhone`, the date window, the elapsed clamp). `tests/forms/parity.test.ts` compares client and server on about 350 good and bad inputs plus a seeded fuzz corpus (20,870 candidate values) across every field of every form, and asserts outcomes, so a rule change that is not copied fails. The rule sets (`NAME_RULES`, `SHORT_RULES` and the others) are still copied in `rules.ts`; the better fix is a zod-free rule module imported by both (request R1, open).
  - **R-PHONE:** before validating a phone number, remove U+00A0, U+2007, U+2009, U+202F, U+200B, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069 and U+FEFF; then apply the separator and digit rules. A number pasted from WhatsApp or Contacts is accepted.
  - **R-TEXT:** single-line free-text fields (event, venue, budget, fee, organisation, company) additionally allow the rupee sign, en dash, em dash, curly single and double quotes, `%`, `!`, `?` and the middle dot. Control characters, CR and LF, angle brackets, braces, square brackets, backslash, pipe, backtick, `;`, `*`, `_` and a leading `=` stay refused. A person's name (`NAME_CHARS_RE`) is deliberately unchanged.
  - **R-DATE:** a coverage or tournament start date must be a real calendar date from yesterday (IST) to 1,095 days after today (IST); code `date_out_of_range`, message "Please check the date: it should be from yesterday up to three years ahead." The clock is injectable on both sides. End dates and `startMonth` keep the plain rule (real date, 2000 to 2100, end not before start).
  - **R-ELAPSED:** the server clamps `elapsedMs` into 0 to 86,400,000 (a non-integer counts as 0) and never rejects for it; the client clamps, restarts its timer after every send, and a retry without an edit sends no timer (a quick "Try again" must not look like a bot, because under 1,000 ms is `rate_limited`).
  - **Trimmed value:** the client checks the same trimmed value `buildPayload` sends (B-13).
  - **Paths and UTM:** `source.path` and event paths need one leading slash (`//x`, `/\x`, `/a//b` and `..` are refused); UTM values allow letters, marks, digits, space and `_ . -`, never a leading `= + - @` (S-14).
  - **Text sanitiser:** the URL-detection pattern was made linear-time (S-4: 1,500 hyphens-then-Tamil characters 0.16 ms against 139 ms before); the client uses the same module.
  - No public text carries an example phone number (the `invalid_phone` message was reworded without digits), so the privacy scan has no exception for one.
- **Consequences.** Two places to change a rule; the parity test is the net. Tests that call `validateLeadRequest(payload)` without `{ now }` use the real clock. `endDate` and `startMonth` are not bounded above or below by a window; if the owner wants that, it is a one-line rule on each side.
- **Status.** adopted.
- **Sources.** `docs/m1/forms-notes.md` P1 and deviation 1; `docs/m1/fix-forms-notes.md` sections 1, 3 (B-1, B-2, B-4, B-13, B-18); `docs/m1/fix-backend-notes.md` B-1 to B-4, B-18, S-4, S-14; shared rules R-PHONE, R-TEXT, R-DATE, R-ELAPSED; `docs/m1/infra-notes.md` R3.

## D-063 Security headers and CSP: one header policy with build-time hashes

- **Context.** D-029 wants a CSP with script hashes. Prerendered pages are static assets, so Astro middleware does not run for them and per-request nonces are impossible; `_headers` allows 100 rules and 2,000 characters per line and is not applied to Worker responses; the Cloudflare adapter 14.3.4 writes no CSP; Astro's own `security.csp` emits a `<meta>` tag only (no `frame-ancestors`).
- **Decision.**
  - **One CSP header** built by `src/lib/infra/headers.ts` (pure): `default-src 'self'`; `script-src 'self'` plus the SHA-256 of every unique inline script block, `https://challenges.cloudflare.com` and (only with an analytics token) `https://static.cloudflareinsights.com/beacon.min.js`; `style-src 'self'` plus hashes; `style-src-attr 'unsafe-inline'` (a `style` attribute cannot run code); `script-src-attr 'none'` (no inline event handlers); `connect-src 'self'` plus `https://cloudflareinsights.com` (with a token) and the Supabase origin (only when set); `frame-src` the YouTube privacy domain and Turnstile; no `unsafe-eval`, no `unsafe-inline` for scripts or style blocks. Worker responses get a hash-less policy. Fixed headers: `Referrer-Policy: strict-origin-when-cross-origin` (never `no-referrer`: the analytics beacon needs a Referer or Origin), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a restrictive Permissions-Policy, and HSTS only when `PUBLIC_HSTS_MAX_AGE` is set (set it after the real domain is live, start short; no `includeSubDomains` or `preload`).
  - **Static pages:** `public/_headers` is generated (a test fails if it drifts from the generator) and the committed file is the fail-safe version with no inline code allowed. After every build `scripts/finalize-headers.ts` rewrites `dist/client/_headers` (the adapter's immutable `/_astro/*` rule first, then ours): hashes added, `X-Robots-Tag: noindex, nofollow` on every page unless indexing is on (D-056); it fails the build on an inline event handler or a line over 2,000 characters. No `Cache-Control` goes in a `/*` rule (it would stop the adapter adding the immutable block).
  - **Worker responses** (`/api/*`, `/go/*`, error pages): `src/middleware.ts` applies the headers and never overwrites a header a route set.
  - **Finalisation is a step inside `npm run build`** (`scripts/build.mjs`): `.npmrc` `ignore-scripts=true` makes npm skip pre- and post-hooks, so a `postbuild` entry never runs (observed). A direct `astro build` leaves `_headers` unfinalised; the strict release check catches it.
- **Consequences.** About 30 distinct inline blocks fit in the line limit; above that the build fails (then switch to Astro's `security.csp` meta policy plus a smaller header). Tightening `style-src-attr` needs `build.inlineStylesheets: 'never'` in `astro.config.mjs` (lead's file, optional) and no `style=` attributes in components. The policy has not yet been trialled with `Content-Security-Policy-Report-Only` on a live host; do that at the first preview deploy.
- **Status.** adopted.
- **Sources.** `docs/m1/infra-notes.md` PD-1, PD-2, deviations 1 to 3, R7; `docs/m1/research-notes.md` proposal 4 and item 8; TP-A1.3, TP-A2.4, TP-A3.
- **Amended by D-097 (2026-10-22).** the generated Cloudflare `_headers` file is replaced by Vercel header configuration (`docs/m3/port-B-notes.md`); the policy and the build-time hashes are unchanged.

## D-066 First-party JavaScript budget: 80 KB gzip, measured "on view", strict

- **Context.** Spec 12.5 and D-010 set 80 KB of first-party JavaScript per public page but say nothing about how to measure it. The first measurement (78.3 to 79.2 KB) left out the 0.9 KB site-wide scripts; measured strictly the four form pages were 80.3 KiB, over (review C-1, major). React DOM is about 65.7 KB of every form page.
- **Decision.**
  - **Definition:** 80 KB is read as 80 KiB = 81,920 bytes of gzip (level 9) per public page "on view": every module script, every island entry (`component-url`, `renderer-url`, `before-hydration-url`), the static-import closure of those (each file once), plus every inline executable script (Astro's island and `client:visible` scripts, 2,181 B). JSON-LD and other data blocks are excluded; other-origin scripts (Turnstile, the beacon) are listed, not counted; files reached only through `import()` (fetched after the first touch or on Send) are reported as "lazy" and not counted. `scripts/check-js-budget.ts` (`npm run check:js-budget`) enforces it, is wired into `ci.yml` (fails the run) and is step 7 of `build:strict` (D-065), and prints the heaviest pages and, when one is over, its biggest files.
  - **Measured (2026-10-21, locked build after the Forms trim):** each of the four form pages 77,494 to 77,495 B (75.7 KiB), headroom about 4.4 KB; every other page 717 B; lazy chunks about 15.4 KB in total, so a visitor who fills in and sends a form loads about 92.9 KB. Before the trim: `/book` 82,269 B, `/tournaments/submit` 82,210, `/partner` 81,747, `/contact` 81,295 (two pages over by 349 and 290 B); the checker reproduced the reviewer's figure exactly. React DOM and its Astro glue, `react`, and Astro's two inline scripts are about 71 KB of the 77.5 KB, so with React the forms cannot go below about 76.5 KB. A Vite config switch to remove the preload helper (852 B plus about 280 B) was tried and changed nothing.
  - The first-pass figures in `docs/m1/forms-notes.md` section 2 are superseded.
- **Consequences.** A stricter reading ("everything the page can ever load") would put the form pages about 11 KB over; the lazy figure is printed so the lead can see it.
- **Proposed (needs owner approval; a lead-only dependency change):** alias React to Preact through `@astrojs/preact` and `preact` (about 4 KB gzip against React DOM's 64 to 66 KB; not installed), or write the forms in plain TypeScript. ## D-069 `/go/[slug]` redirect rules and the click-log brake

- **Context.** D-031 and D-029 want counted outbound links without storing personal data. The brief left several details open and reviews found a dot-segment bypass of the internal-link guard (B-7), a non-uuid id written to a uuid column (B-16) and an unthrottled click log (S-15).
- **Decision.**
  - **`/go/[slug]`** is an on-demand route (`src/pages/go/[slug].ts` thin, logic in `src/lib/infra/go.ts` and `go-handler.ts`); the typed link map and the allowed host list live in `src/content/go-links.ts` and are both EMPTY. It answers 302 with UTM, and 404 (not a redirect to `/partner`) for unknown, malformed or expired slugs and for unsafe targets. UTM never overrides a parameter the target already has; `partner` links use `utm_medium=sponsor`; internal links carry no UTM; a date-only expiry lasts through the end of that day in India. Bots, prefetch and HEAD requests are redirected but not counted. The click row has no raw IP and no raw user agent (`ua_hash`), is written with `waitUntil`, and stores `target_id` only when it is a uuid (otherwise it is dropped with one warning per link).

A limited request still redirects; it just writes no row.

Sponsor links currently go straight to the sponsor (`SponsorStrip`); when that changes to `/go/<slug>` the lead switches `features.sponsorLinkTracking` (D-061; a test fails if `go-links.ts` gets a sponsored or partner link while the switch is off). - **Status.** adopted.

## D-078 Protected players in the archive: minimal pages and what they may show

- **Context.** D-012 says protected = every status except `adult_confirmed`; the owner confirmed minimal pages for unknown age (D-076). The review found the first build contradicted D-012 (S2-6, major) and put sponsor strips on protected pages (S2-2, major).
- **Decision.**
  - **Player pages.** `adult_confirmed` with a full match gets a profile (indexable, directory, sitemap, search). `unknown` gets a MINIMAL page only while `unknown_match_mode = noindex_minimal`: noindex, **no name** (H1 "Player page", generic title, opaque address `player-<id>`), a removal link, no stats, list, JSON-LD or share; `MinimalPlayer` has no name field. Minors: no page. A missing id or an unrecognised status counts as unknown (fail closed). `src/lib/archive/protected.ts` is the one place for the rule.
  - **Match pages.** `full` (all participants adult), `listed` (non-Tamil-Nadu event, raw title, no player or tournament links, labelled "All India"), `minimal` (an unknown participant: noindex, generic tab title, description and Open Graph, no parsed details, no links, breadcrumbs-only JSON-LD, no share, opaque address, **not in the match list, related lists, sitemap or JSON**), `hidden` (a minor, hidden event or video, dangling reference: no page, dropped in `model.ts`). The raw YouTube title is the H1 on every kind (D-016); on a minimal page it is the only place a protected name can appear because it is YouTube's own text.
  - **Indexes.** Search index: adult profiles and tournaments only. Match list JSON: full and listed only. Sitemaps: indexable pages only.

## D-081 Suppression, tombstones, retired videos and the 30-day purge

- **Context.** D-014 requires tombstones and D-016 requires stored API data refreshed or deleted before day 30. Review S2-7 found name-only suppression gaps; sync2 found `service_role` has no delete on `videos` (D-014) and matches restrict on it.

## D-082 Parser age-token rules fail closed (and the M2b parser choices)

- **Context.** The review found a critical hole: a bracketed age such as `(U15)` was swallowed as an affiliation and gave no minor signal (B2-1, critical), with vocabulary gaps (B2-2), score and noise handling (B2-3), invalid dates (B2-4) and unbounded input (B2-5). The parser is implemented (`src/lib/parser/parse.ts`, version `1.0.0-m2b.1`); the former red tests are green and `vitest.red.config.ts` is thin (D-017 text about red tests is stale).
- **Decision.** An age scan runs over the WHOLE title and hashtags: bracketed, prefix, trailing and unseparated forms, `U-15`, `U 15`, `15U`, `Under-15`, `Under Fifteen`, `Sub-Jr`, `15 years`, other-script digits, full-width letters. Each is a real minor signal (players `minor_suspected`, `minorHold`). Bracketed ages are never stored as affiliations. Words that look like an age but are unmapped (Kids, School, Jr, Teenagers, `U15A`, bare Under, Tamil junior words, OT-32) raise the hard flag `UNKNOWN_AGE_TOKEN` (always reviewed) and make players `minor_suspected`, without setting `minorHold`. Impossible dates are never stored. `parseTitle` parses at most 300 characters and flags `TRUNCATED_TITLE`. Gold-seed agreement on 70 real titles is agreement with first-guess labels, not correctness: 13 of 38 match-style titles auto-accept (review C2-3 notes the 90% auto-parse target is therefore not met).
- **Consequences.** More titles go to review (the workload the owner sees); fewer minors slip through. The owner spot-check (OT-35) is what makes the gold set true. Open: PF-041 (Tamil vocabulary, needs a native reviewer), a noise word in the middle of a name, and "senior" in a free-text tournament name.

## D-083 Identity resolution: exact aliases, tiers, no similarity merging

- **Context.** First names such as GANESH identify dozens of people (D-013, PC-01). Merging by similarity would join strangers.
- **Decision.** `src/lib/identity` and `src/lib/sync/identity.ts`. Tiers: one confirmed in-scope alias links (`exact_alias`); two or more candidates are `AMBIGUOUS_ALIAS` (nothing linked, match demoted to held, reason added to the video's review reasons, parse_status `needs_review`); two or more name tokens, at least one a real word, with no alias create or reuse a PROVISIONAL player scoped to the tournament edition; single tokens, initials, truncated and blocked names stay plain text; a rejected alias never links; the same person is never linked twice in one match. Similarity only produces `possible_duplicate` audit rows (ids and counts, no names) and the admin's duplicate list; `matches.duplicate_of` is never set automatically. Only `type = match`, parse kind `match`, not international, Tamil Nadu scope (D-018, D-076) and fully public videos create entities. New players start with the parser's participation status, an opaque slug, no district, photo, bio or handle, noindex, hidden, provisional; a minor signal only raises, never lowers. Tournaments key on `(series_key, edition_year)`, spelling variants through `tournament_aliases`; new rows are `pending` and `hidden` until the admin approves (this default awaits the owner). Matches are `published` only when `auto_publish_clean_parses = true` and the parse is clean; the sync never promotes a held match. Field locks and `resolution = manual` slots are never rewritten. Merge: more restrictive status wins; minor plus adult_confirmed is refused without a logged override; a suppressed player can never be merged. Split: the new person inherits status and signals, is provisional and hidden, and the parent gets `rejected` aliases (PC-02). Alias ranking is confirmed over rejected over provisional, and a merge always keeps the dropped name as a confirmed alias (B2-13, fixed with `tests/admin/roundtrip.test.ts`). The run is idempotent: `reparse` leaves both stores byte-identical, spends no quota, marks nothing dirty.
- **Consequences.** Fewer wrong merges; more manual confirmation by the owner.
- **Status.** adopted.
- **Sources.** `docs/m2/sync2-notes.md` (Identity resolution); `docs/m2/admin-notes.md` (Rules enforced, B2-13); reviews B2-13 to B2-15, C2-4.
