## 5. Proposed decisions (the lead records them in `docs/DECISIONS.md`)

**P-F1 Turnstile test keys.** Context: S-1: the published test secret accepts any token and skipped hostname and action checks, and could reach production through a copied example or a pasted dev value. Decision: test secrets are accepted only with `TURNSTILE_ALLOW_TEST_KEYS=true`; otherwise the lead endpoint fails closed (`degraded`) and `/api/health` reports `ready:false, reason:turnstile_test_key`; no auto-detection; no test secret value is seeded in `.env.example`; health shows `testMode:true` while allowed. Consequences: a dev machine needs two lines in `.dev.vars`; the release gate and the secret loader should also refuse a test secret (request below).

**P-F2 Owner alert contents (needs the owner's yes before the switch is ever turned on).** Context: S-5 and C-4: the wa.me link in every alert put the unverified customer phone on Telegram, outside D-029 and the processors story in D-028. Decision: default alert = kind, reference, first name or initial, source page and a pointer to Supabase Studio (until the M3 admin); the customer's WhatsApp reply link and the district only when `TELEGRAM_ALERT_PHONE_LINK` is exactly `true`; the owner email follows the same switch. The privacy page states the default (done by Legal). Consequences: until the M3 admin exists the owner opens Supabase Studio to reply; a "NOT SAVED" alert has no contact details by default (the visitor is shown a WhatsApp link quoting the reference, so the owner watches WhatsApp). The owner and the lawyer may switch it on; the privacy sentence for that case already exists.

**P-F3 Global circuit breaker and email aliases.** Decision: at most `LEAD_GLOBAL_HOURLY_CAP` (default 40) accepted enquiries per hour across all visitors, then 429 plus one owner notice per hour; the per-email limit and the once-a-day acknowledgement use a key with `+tag` and Gmail dots folded. Consequences: a real rush above the cap is sent to WhatsApp for the rest of the hour (the owner is told); tune the number after traffic. Not done: an acknowledgement limit per IP, an email-ownership check.

**P-F4 Consent evidence tables.** Decision: migration 0002 adds `notice_versions` and the append-only `consent_events` (section 2, C-10); D-028's suppression list, erasure log and withdrawal flow move to M3/Phase 2. Consequences: the database stores the exact notice text and its hash per version; consent rows are never edited.

**P-F5 Health response and monitor keyword.** Decision: `/api/health` body `{ok, service, lead, ready, reason?, testMode?}`, HTTP 200 always, `reason` one of `missing_secrets`, `supabase_url`, `turnstile_test_key`. Consequences: the uptime keyword must be `"lead":"ready"` (section 0).

**P-F6 Secret destination and default privileges.** Decision: the secret key is only sent to `https://<ref>.supabase.co` (override for loopback in local dev); migration 0001 revokes default grants for anon/authenticated on future public tables, sequences and functions, and the assertions script checks every table in `public`. Consequences: a custom Supabase domain would need a code change and a decision; every future table is closed by default.

## 9. Known limits (not defects of the fixes)

- The default alert drops the district (a visitor-typed value); the brief lists only kind, reference, first name, page and the pointer.
- The per-IP counter counts attempts, not outcomes (20 an hour, generous for carrier NAT).
- The Gmail dot rule applies only to Gmail; other providers keep dots, and `+tag` is removed everywhere (a mailbox whose real name contains a plus would share a key with its base name; rare).
- `endDate` has no window of its own (it must be a real date and not before the start).
- A visitor on an old open tab (unknown notice version) gets a consent row without a hash.
- The flood notice needs the counter store; with counters down it stays silent (by design: no notice flood).
