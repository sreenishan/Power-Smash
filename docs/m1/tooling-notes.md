### Finding E-1 (real, in the forms, not fixed here): the first tap on Send is lost on `/contact/` and `/alerts/`

On the two one-step forms, tapping Send as the very first touch (no field touched before) does nothing; the second tap shows the errors. Cause (not confirmed in code): the same pointer-down marks the form as started, the spam-check box (shown on step one of these forms) switches from its placeholder to the widget area, and the click no longer lands on the button. The multi-step forms are not affected (the spam-check box is on a later step). A visitor who taps a field first is not affected. The test `a first tap on Send with no earlier touch still shows the errors` is marked `test.fail` for these two pages: it passes the suite while the bug is open and reports "Expected to fail, but passed" once it is fixed, which is the cue to delete the marker. Owner: Forms worker (`LeadForm.tsx`, `TurnstileWidget.tsx`).

## 3. Local PostgreSQL (Part B)

- `node scripts/pg-local.mjs <init|start|stop|status|reset|apply|check|proposed|all>` (`npm run pg:local -- <command>`). Cluster in `tools/pgdata/` (git-ignored): `trust` authentication, `listen_addresses=127.0.0.1`, port **54329**, superuser `postgres`, no passwords. Always `stop` it when done. `start` runs `pg_ctl` with ignored stdio on purpose (the server inherits pipes and a plain `spawnSync` would never return).
- `supabase/local/roles.sql` (local only, never on a hosted project): creates `anon`, `authenticated`, `service_role` (bypassrls), `authenticator`, gives `usage` on `public`, and sets the Supabase-style default privileges for role `postgres` in `public` (ALL on future tables, sequences and functions to the three API roles), so the migrations' revokes are tested against the worst case, not an empty one.
- `apply` runs `roles.sql`, then `supabase/migrations/*.sql` in order. `check` runs `supabase/checks/*.sql` (each must return its "ok" row). `proposed` builds a fresh scratch database `psscratch` with the migrations plus `supabase/proposed/0003_lead_kinds_m3.sql` and runs the checks.
- Test `tests/supabase/local-pg.test.mjs` (10 tests): SKIPPED unless the local server is already up (`pg_isready` on 54329). It uses its own database `pstest` and drops it. It covers: both migrations apply and both check files return ok; `service_role` inserts into every Worker table (the lead trigger writes the `created` event); `service_role` updates leads but cannot delete or truncate them; a wrong notice hash is refused; `anon` and `authenticated` are denied select, insert, update and delete on every table in `public` and cannot call `app` functions; `consent_events` and `notice_versions` refuse update, delete and truncate (the owner role gets the "append-only" error, `service_role` a permission error); 0003 is refused before and accepted after (`video_submission`, `alerts_signup`).

### Results of the first real SQL run (2026-10-22)

- Both migrations applied with no syntax or runtime error on PostgreSQL 17.11. `0003` applied in the scratch database.
- First run of `checks/0001_assertions.sql` FAILED: `service_role can delete from public.leads (retention anonymises, it does not delete)`.

### Finding S-1 (real bug, fixed in the migrations)

The migrations revoked the default privileges from `public, anon, authenticated` only, then granted `service_role` the exact list. With Supabase's default privileges (which give `service_role` ALL on every new table created by `postgres`, and which `roles.sql` reproduces) `service_role` therefore kept `DELETE`, `TRUNCATE`, `REFERENCES` and `TRIGGER` everywhere. Effect: the Worker's key could delete leads (retention is meant to anonymise), and could truncate the "append-only" consent tables (the triggers refuse it for everyone, but the privilege should not exist, and the 0002 check asserts it). On a hosted project created before the 2026-10-30 change the same defaults apply. Fix, plain: `service_role` is added to the `revoke all on table ...` lists of `0001_lead_funnel.sql` (the six tables) and `0002_consent_records.sql` (the two tables), before the explicit grants, with a comment. The static tests (`tests/supabase/migrations-structure.test.ts`) still pass; after the fix both checks return ok on `psdev` and `psscratch`. Because the migrations had never been applied anywhere, editing them is allowed (no renumbering). Nothing else in the SQL needed changing.

Not verified here: Supabase's own extras that a hosted project has (the `auth` and `storage` schemas, `supabase_admin`, PostgREST). The REST-level check stays `scripts/anon-harness.mjs` against the dev project (OT-03); this run proves the privilege and trigger rules in plain PostgreSQL, not the API layer.
