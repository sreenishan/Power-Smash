### Added after the independent security review (2026-10-22): prove these on the first preview
8. **Host-conditional noindex routes** (`src/lib/infra/vercel-routes.ts`, only emitted when `PUBLIC_ALLOW_INDEXING=true`) use host matchers in object form (`{suf}`, `{eq}`). The installed `@vercel/routing-utils` 6.6.0 types accept that form, but no real deploy has used it. Do one preview with `PUBLIC_ALLOW_INDEXING=true` and `PUBLIC_SITE_URL` set to a non-vercel host, then `curl -I` the `.vercel.app` address and expect `X-Robots-Tag: noindex`; if the deploy is refused or the header is missing, fix before G1.
9. **Spoofed client IP.** Send `X-Forwarded-For` and `X-Vercel-Forwarded-For` with a made-up address to `/api/lead` (dev project, test mode) and confirm the stored `ip_hash` does not follow them (VF-V9 says Vercel overwrites them).
10. **Same-origin check scheme.** `sameOriginAllowed` (`src/lib/leads/handler.ts`) compares the `Origin` with `request.url`. On a preview with no `PUBLIC_SITE_URL`, an `http` request URL against an `https` Origin would answer 403. Post a real form on the first preview and read the answer.
11. **Function region.** `.vercel/output/functions/*/.vc-config.json` carries no `regions`; whether `vercel.json` applies to a prebuilt deploy is unknown, so the dashboard setting (OT-02) is the one that counts. After the first deploy read the region in the Vercel project (and update the privacy provider row if it is not Mumbai).
12. **`/_image`** answers 404 (see `docs/m3/review-fix-code-notes.md`), and a Git push on a connected repo does not create a deployment (see `docs/m3/review-fix-infra-notes.md`, `vercel.json` `git.deploymentEnabled`).
13. **`SUPABASE_URL` baked fallback.** With only the GitHub build variable `PUBLIC_SUPABASE_URL` set (no runtime `SUPABASE_URL`), a `/go/<sponsor>` click must still log and the admin API must still answer. `/api/health` cannot show this; test it by hand.

Turnstile `siteverify` is a plain `fetch` to `challenges.cloudflare.com`, host-independent; `TURNSTILE_EXPECTED_HOSTNAMES` must now list the Vercel and real hostnames.

Findings to fix (not mine to edit):
1. **`waitUntil` via `cfContext` is Cloudflare-only.** `src/pages/api/lead.ts`, `src/pages/api/placements.ts` and `src/pages/go/[slug].ts` read `locals.cfContext.waitUntil`. On the Vercel adapter that is undefined. Effects: the lead handler falls back to awaiting the owner alert before answering (safe, a little slower; `runLater` returns the promise). `/go/[slug]` falls back to `void p.catch(...)`, i.e. fire-and-forget after the response: on a Vercel function the click-log insert may be cut off when the function freezes after the response (behaviour not verified in `vercel-facts.md`). Recommend: await the click write with a short timeout before returning the 302, or use Vercel's `waitUntil` (a new dependency, lead only, not researched). The unit test `tests/infra/go-handler.test.ts` should keep passing either way.
2. **`/api/placements` caching.** The route uses `caches.default` (Workers Cache API); on Node it is null, so every sponsor-slot page view reads Supabase. Its response sets `Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=600`, but area B's route rules put `Cache-Control: no-store` on every `/api` path (`ROUTE_SRC` for `/api`, `docs/m3/port-B-notes.md`). Which one wins on Vercel is unverified; if `no-store` wins, D-009's "cache `/api/placements` at the edge" intent is lost and database reads grow with traffic. Suggest B exempt `/api/placements` from `no-store`, then test on the first preview. `purgePlacementsCache` after an admin edit is also a no-op without the Cache API.
3. **Stale comments** (no behaviour): `leads/handler.ts` line 69 ("Client IP from Cloudflare (`cf-connecting-ip`)") and the `waitUntil` doc ("Cloudflare `ctx.waitUntil`"); "On-demand Worker endpoint" in lead.ts, event.ts, health.ts, placement-beacon.ts, placements.ts, go/[slug].ts; `notify/alerts.ts` and `notify/telegram.ts` ("Worker variable TELEGRAM_ALERT_PHONE_LINK"); `src/lib/security/ratelimit.ts` header ("Workers Rate Limiting binding"). The optional `LEAD_RATE_LIMITER` and `EVENT_RATE_LIMITER` bindings remain in `runtime-env.ts` types and `ipLimiter` / `limiter` deps; harmless (always undefined). Per-IP limiting now rests on the database counter and global caps (D-044) only; R-45 records this.
4. **`/api/health` ("runs in the Worker")**: fine on Vercel (no outbound call). The uptime keyword `"lead":"ready"` is unchanged.
5. **Admin hostname.** The docs assume the admin is still served under `/admin/` or its own hostname; `ADMIN_ALLOWED_ORIGINS` must list the real hostname. Not verified in code.
6. **`.gitignore` does not yet list `.vercel`.** The adapter and `vercel link` create `.vercel/` (build output with 15,000+ files, project ids). `.vercel` must be git-ignored before the first commit; SECRETS.md says it is. Area D owns `.gitignore`.
7. **Env var scopes and build-time reads.** `astro.config.mjs` reads `process.env.PUBLIC_SITE_URL` at build time; with the prebuilt flow the build runs on GitHub, so `PUBLIC_*` values are GitHub repository variables, and Vercel Production variables are runtime-only. The docs say so (OT-02 step 6). A page that reads a runtime-only name at build time would silently get `undefined` on the prebuilt path.
