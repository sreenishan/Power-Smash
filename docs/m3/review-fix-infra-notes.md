# Review fix wave: deploy pipeline (fix-infra), 2026-10-22

Four defects from the independent security review of the Vercel port. Nothing was run against a real Vercel, GitHub or Supabase account; no token or real value was used. Only the repository files named below changed.

## FIX 1: Vercel's own Git integration (medium)

- `vercel.json`: added `"git": { "deploymentEnabled": false }` (the file is now `regions` + `git`).
- Doc relied on: https://vercel.com/docs/project-configuration/git-configuration (page dated 2026-08-25). `git.deploymentEnabled` is a Boolean or a branch map, default `true`; `false` "turns off automatic deployments for all branches". The exact property name and the form `false` are confirmed there.
- `ignoreCommand` was checked (https://vercel.com/docs/project-configuration/vercel-json, section ignoreCommand; https://vercel.com/docs/project-configuration/project-settings, "Ignored Build Step") and deliberately NOT added. It runs when a deployment enters the BUILDING state (exit 0 cancels, exit 1 continues). No page says it is skipped for `vercel deploy --prebuilt`, so an `exit 0` could block the real deploy path. With `git.deploymentEnabled: false` no Git deployment is created at all, so the second guard buys little and risks a lot.
- NOT settled by the docs (first-preview check): none of the pages says in words that `git.deploymentEnabled: false` leaves `vercel deploy --prebuilt` (CLI) alone. The property is described only as a rule for Git commits ("should not trigger a deployment upon commits"), and CLI uploads are not commits, so it should not block them. Treat the first `preview.yml` run as the proof: if it is refused, remove the property and rely on the owner's disconnect (OT-02).
- Limits, say plainly to the owner: the setting is read from the repository, so it protects against a forgotten dashboard setting, not against someone who can push a branch that edits `vercel.json`. The owner still disconnects the repository in Vercel (OT-02); `deploy.yml`'s header now says so.
- Tests: `tests/infra/workflow-guards.test.ts` (describe "vercel.json"): `git` equals `{ deploymentEnabled: false }`, region kept, no `crons`, no `ignoreCommand`, no deprecated `github` switch, no build or output settings.

## FIX 2: main-only guard on the secret-holding jobs (low)

- Job-level `if:` is now `vars.X_ENABLED == 'true' && github.ref == 'refs/heads/main'` in `sync.yml:44`, `backup.yml:51`, `retention.yml:43` and `restore.yml:45` (`deploy.yml:63` already had it). `restore.yml` does hold credentials (`DEV_SUPABASE_DB_URL`, `AGE_DRILL_KEY`; dev data only), so it got the guard too. The STATUS comment at the top of each file says so.
- Scheduled runs always run on the default branch, so they pass the check. Admin "Sync now" and "Publish now" dispatch with `ref: main` (tests/admin/handler.test.ts), so they pass too. A manual run started from another branch is now skipped.
- Every action is still pinned to a full SHA; no `pull_request_target` anywhere (tests still assert both).
- Future-proofing: `tests/infra/workflow-guards.test.ts` reads every file in `.github/workflows/` and fails if a job references a repository secret (anything except `GITHUB_TOKEN`; `secrets: inherit`, `secrets[` and `toJSON(secrets)` count as opaque and also fail) unless its `if:` matches exactly `${{ vars.<NAME>_ENABLED == 'true' && github.ref == 'refs/heads/main' }}` (an `||` or a missing switch fails). The checker has its own tests with synthetic workflows.
- Documented exception, residual risk: `preview.yml` must run on pull-request branches, so it is exempt, and only for `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`. A Vercel token is not scoped to "previews only", so edited YAML on a branch in this repository could run `--prod` with it. This is acceptable only while the owner alone can push branches (already stated in `preview.yml`). A stronger fix needs a separate Vercel team or project for previews with its own token (owner decision, not done).

- Generated with `npm install --package-lock-only --ignore-scripts` inside the folder (no `node_modules` was created; nothing was installed or executed). It worked first time: no missing or too-young version.
- Checked against the registry: all 372 distinct name@version pairs in the lock are at least 7 days old (youngest: `undici` 6.29.1 and 7.30.1, 7.04 days); the one name that did not resolve by name (`path-to-regexp-updated`) is an npm alias of `path-to-regexp@6.3.0` from 2024. Only two packages declare an install script: `esbuild@0.27.0` and `fsevents@2.3.3` (macOS only); with ignore-scripts they do not run. The six `@vercel/vc-native-*` binaries are optional per-platform packages without install scripts.

The npm cache key in `setup-node` now covers both lockfiles (`cache-dependency-path`).

## FIX 4: `--sensitive` in the secrets loader (low to medium)

- Docs relied on: https://vercel.com/docs/environment-variables/sensitive-environment-variables (dated 2026-08-28) and https://vercel.com/docs/cli/env (dated 2026-08-20).
- What the docs say (current text): variables are now "Config" (readable after saving) or "Secret" (write-only after saving); old "Sensitive" variables are treated as Secrets. `vercel env add NAME <environment> --sensitive` stores a Secret (`--no-sensitive` stores Config; `--type secret|config` is the explicit form; `--sensitive` with a conflicting `--type` is an error). The CLI table says the default type for Production, Preview and custom environments is already `secret` and for Development `config`. Secrets are now allowed in Development ("this reverses the earlier rule"), so the old "not in Development" statement is outdated in the current text, but it was true in older docs and older CLI versions. Build logs redact a Secret of 32 characters or more.
- `scripts/load-secrets.mjs`: `vercelEnvAddArgs(name, scope)` (line 184) adds `--sensitive` for Production and Preview and not for any other scope; the loader only writes Production (`VERCEL_SCOPE`, line 98), so every Vercel send is `env add NAME production --sensitive`. The flag is explicit even though the current docs say Production defaults to Secret, so it does not depend on which default a given CLI version has. Every name the loader sends to Vercel is a server-side runtime secret (docs/SECRETS.md key matrix), so there is no readable opt-out; public build values never go to Vercel from this loader (they go to GitHub variables).
- Unchanged rules, still tested: values only on standard input, never printed (redactor), Turnstile published test secrets refused, `--dry-run` prints names only. New: the dry-run and the real run show `Vercel env (Production, sensitive)` and one plain-English line telling the owner the values cannot be shown again.
- Tests: `tests/infra/load-secrets.test.ts` (updated assertions plus describe "Vercel values are stored as sensitive": every Vercel-target name in the manifest is sent with `--sensitive`, no `--value`, value only on stdin; Development gets no flag; Turnstile test secret still refused; the loader's pinned CLI version equals `ci/vercel-cli`). A `--dry-run` with three obviously fake values from a temp file outside the repository worked and was deleted.
- UNVERIFIED: the real `vercel env add ... --sensitive` call against the pinned CLI 64.2.0 (not run; the docs describe the current CLI).

### Owner-facing consequence (for docs/SECRETS.md)

After the loader runs, a Vercel Production secret cannot be viewed again in the Vercel dashboard, and `vercel env pull` cannot read it either: it can only be replaced (Project > Settings > Environment Variables > Edit, then type the new value). So the owner keeps the value in the password manager, not in Vercel; a lost value is rotated, not recovered. A Sensitive variable cannot be turned back into a readable one in place (delete and re-create). Two practical points: running the loader again for a name that already exists on Vercel may be refused by `vercel env add` (the docs describe `--force` as the way to overwrite; the loader does not use it on purpose, because overwriting a live production value is a rotation and needs the owner's yes), so the line in the loader's failure message "sending twice is harmless" is true for GitHub but not for Vercel; and the Vercel team policy "Separate Production Secret Values" (optional, owner role) would require Production to use a different value from Preview.
