# M4 infra worker notes: restore drill and retention job

Written 2026-10-22. Nothing here is switched on; nothing was run on GitHub or against any real project.

## Restore drill (D-011 part 1)
- `.github/workflows/restore.yml`: monthly (5th, 22:17 UTC) and on demand; the job runs only when the repository variable `RESTORE_DRILL_ENABLED` is `true`.
  Owner inputs (new names): secret `DEV_SUPABASE_DB_URL` (read-only session-pooler string of the DEV project, made-up data only), variable `AGE_DRILL_PUBLIC_KEY`, secret `AGE_DRILL_KEY` (`node scripts/make-age-keys.mjs --drill`). Add the three names to `docs/SECRETS.md` when the owner is asked.
- Flow: dump dev with the same `pg_dump | age` line as `backup.yml` (to the drill key), decrypt with `AGE_DRILL_KEY` straight into `pg_restore` in a `postgres:17` service container (schemas `public`, `app`, `api`, `--exit-on-error`), run `scripts/restore-drill-erasure.sql`, compare per-table row counts with the counts taken from dev just before the dump, run `scripts/restore-drill.sql` (RLS on, no anon/authenticated privilege on tables, sequences or functions in `public`/`app`) and every `supabase/checks/*.sql`.
- No new action: only `actions/checkout` at the SHA already in `ci.yml` (a test enforces "same SHA as ci.yml"). The production key and `SUPABASE_DB_URL` are not used.
- Limits: the backup script is inlined in `backup.yml`, so the dump line is duplicated here (a test compares the two lines); the dev project cannot be proven made-up by the job, only by convention (D-004); Supabase `auth`/`storage` schemas are not restored (documented residual risk, D-011); `erasure_log` does not exist yet, so the erasure step prints a notice. When it is built, its migration must add `app.reapply_erasure_log()` or the drill fails on purpose.
- Local equivalent: `node scripts/pg-local.mjs start`, `node scripts/restore-drill.mjs`, `node scripts/pg-local.mjs stop`. Generates fictional rows, dumps, restores, compares counts, runs the SQL assertions and all checks, drops both databases. **`age` is not installed on this PC, so the local run used the plain path; encryption is verified only in CI.** The script uses `age`/`age-keygen` with a throwaway key if they are on PATH. Nothing was downloaded.
- The drill found that the check files assume an empty database; `0010_assertions.sql` is written relative to existing rows. Other check files passed on the populated copy.

## Retention job (D-028, spec 15.4, R-31)
- Migration `0010_retention.sql` + `supabase/checks/0010_assertions.sql`. `public.admin_run_retention(p_actor, p_dry_run default true)`, service_role only, SECURITY DEFINER, `search_path = ''`, returns counts only.
  - Leads with status `completed` or `lost` whose `updated_at` is older than 24 months: name -> `Anonymised`, organisation, phone, email, notes, lost reason, `ip_hash`, payload cleared, `anonymised_at` set. Counters and non-identifying fields stay. New column `anonymised_at`; `leads_has_contact` now also accepts an anonymised lead. `won`, `new`, `contacted`, `quoted` leads are never touched. "Closed" is read as `completed` or `lost`; the clock is `updated_at` (there is no closed-at column). Owner/lawyer may prefer a different clock.
  - `rate_limit_hits` older than 2 days and `daily_salts` older than 2 IST days are deleted (D-029).
  - Event documents: no table exists and the rule is held back (D-019, `eventDocuments`); the result says `"event_documents": "not_built"`. Add the step with the table.
  - Not done (needs daily aggregates first): 90-day purge of `events` and `outbound_clicks`.
  - Never touched: `suppression`, `audit_log`, `consent_events`, `notice_versions`, `lead_events`, `tournament_private`. A dry run writes nothing, not even audit. A real run that changed something writes one `retention_run` audit row with counts only. A second run is a no-op.
- `.github/workflows/retention.yml`: weekly (Sunday 22:41 UTC) and on demand; runs only when `RETENTION_ENABLED` is `true`. Manual runs have `dry_run` (default true); the schedule is real. It calls the RPC over REST with `SUPABASE_URL` and `SUPABASE_SECRET_KEY` (same secret names as `sync.yml`); the key goes through curl stdin; the URL is checked against `https://<20 chars>.supabase.co` before the key is sent. No action, no checkout. Switching it on needs the owner's yes and the migration applied to production (0010 changes a constraint on `leads`).
- Tests: `tests/infra/restore-workflow.test.ts`, `tests/infra/retention-workflow.test.ts`, `tests/supabase/retention-migration.test.ts` (static, plus real runs on the local PostgreSQL, skipped when it is down). The anon harness manifest is unchanged (no new table).
